QA 21,606건 전체를 임베딩 → pgvector 적재 → 검색 확인까지 완료.
**임베딩·리랭커를 다시 구성하는 중.**

## 권장 구성

### 지식베이스는 한 종류로 유지

```sql
CREATE TABLE qa_documents (
    id          bigserial PRIMARY KEY,
    question    text NOT NULL,      -- 임베딩 대상
    answer      text NOT NULL,      -- 페이로드
    embedding   vector(768),
    -- 메타데이터
    department  varchar(20),        -- 내과/안과/외과/치과/피부과
    life_cycle  varchar(10),        -- 자견/성견/노령견
    disease     varchar(50),
    source      varchar(30) NOT NULL DEFAULT 'aihub'   -- ★ 반드시
);
```

**`source` 컬럼이 핵심.** 어떤 데이터를 추가하든 `WHERE source = 'aihub'`로 즉시
되돌릴 수 있다. 이게 없이 섞으면 롤백하려고 전체를 재구축해야 한다.

### 임베딩 대상 = 질문(`input`)

질문으로 인덱싱하고 답변(`output`)은 페이로드로 둔다.
사용자 질문 ↔ 저장된 질문 매칭이 의미적으로 더 잘 맞는다.
input의 82%가 실제 의문문 형태라 이 전략이 유효하다.

`instruction`은 인덱싱하지 않는다 (40종 변형이지만 전부 같은 말, 노이즈).

### 검색 파이프라인

```
사용자 질문(한국어)
  ↓
① 벡터 검색       pgvector, top 20        ← 널널하게
  ↓
② 리랭킹          cross-encoder, top 3    ← 여기서 정밀도 확보
  ↓
③ 생성            Gemini + 시스템 프롬프트
  ↓
답변 + 출처(진료과/질병)
```

1단계 top_k를 3이 아니라 20으로 잡고 2단계에서 3개를 고르는 구조.
**리랭커는 나중에 어떤 데이터를 추가하더라도 방파제 역할을 한다** —
질 낮은 데이터가 "정말 관련 있을 때만" 통과하고 평소엔 걸러진다.

### 메타데이터 필터

질문에서 `department` / `life_cycle`을 추출할 수 있으면 검색 범위를 좁힌다.
치과 879건, 안과 1,085건은 필터 없이는 내과 11,049건에 묻힌다.

```sql
WHERE department = '치과'
ORDER BY embedding <=> :q_embedding LIMIT 20
```

`disease`는 77%가 "기타"라 필터로 부적합. 출처 표기용으로만.

### 시스템 프롬프트에 강제할 것

- 검색 결과에 없는 내용은 답하지 말 것 (환각 차단)
- 진단·처방 단정 금지, 동물병원 진료 권유
- **구체적 치료비 언급 금지** — 원본 답변 3%에 비용이 들어있어 그대로 새어나갈 수 있다

## 평가 전략

### 왜 지금 급한가

기준선 없이 데이터를 넣거나 파라미터를 바꾸면 **좋아졌는지 나빠졌는지 알 방법이 없다.**
체감으로는 절대 판단되지 않는다.

### 방법 — Validation을 인덱스에서 빼기

```
지식베이스(pgvector)  ← Training 19,206건
평가용 질문           ← Validation 2,400건 (인덱스에 없음)
```

Validation 질문을 던져 **같은 진료과·같은 질병의 QA가 상위 k에 들어오는지**로
Recall@k를 측정한다. 두 집합 간 질문 누수가 1건뿐이라 평가셋으로 깨끗하다.

**21,606건 전부를 인덱싱하면 질문이 자기 자신을 찾아내 정확도가 100%로 나온다.**
아무 의미 없는 숫자가 된다. 지금 상태가 이렇다.

발표 자료에 "Recall@5 = 0.8X"를 넣을 수 있느냐 없느냐의 차이.

### 실전 문체 검증 (2단계)

AI Hub 질문은 평균 330자 문어체로 잘 정제돼 있다. 실사용자는 그렇게 묻지 않는다.

```
AI Hub:  "진돗개의 수컷이 녹내장으로 의심됩니다. 천장 조명이나 휴대폰의
          후레시로 비추어보면 왼쪽 눈에서만 초록빛이 도는 것을..."       (330자)
실사용:  "우리 개 눈이 밤에 초록색으로 빛나는데 정상인가요"              (126자 수준)
```

**우리 시스템은 전자로만 검증됐으므로 후자에서 무너질 가능성이 크다.
데모 때 터지는 전형적인 사고.**

#### 방법: Validation 질문을 구어체로 변형

```
원본(Validation)  →  LLM으로 구어체 축약  →  변형 질문
```

| | Recall@3 |
|---|---|
| 원본 문어체 질문 | 기준선 |
| 구어체로 축약한 같은 질문 | 실전 성능 |

**같은 질문, 문체만 다르다.** 변수가 완벽히 통제되고, 원본 QA 쌍을 알기 때문에
자동 채점된다. "구어체에서 성능이 얼마나 떨어진다"를 숫자로 말할 수 있다.

#### HF 데이터셋(영어)을 그대로 쓰면 안 되는 이유

영어 질문을 그대로 던지면 실패 원인이 **문체 때문인지 언어 때문인지 구분 불가**하다.
실험은 변수 하나만 바꿔야 의미가 있다.
(다국어 임베딩 모델을 쓰더라도 cross-lingual 검색은 동일 언어보다 체계적으로
정확도가 낮아 성능을 실제보다 나쁘게 측정하게 된다.)

번역해서 쓸 수는 있지만 함정이 있다 — LLM이 문장을 **다듬어버린다**:

```
원문:      "my dogs eye is glowing green at night is that normal"
나쁜 번역: "저희 강아지의 눈이 야간에 녹색으로 빛나는 현상이 관찰되는데,
            이것이 정상적인 반응인지 궁금합니다."      ← 다시 문어체, 테스트 의미 상실
좋은 번역: "우리 개 눈이 밤에 초록색으로 빛나는데 정상인가요"
```

오타·짧은 길이·반말 어투·맥락 생략을 **일부러 보존**하라고 명시해야 한다.
게다가 정답 라벨이 없어 자동 채점이 안 된다.

**→ HF 데이터셋은 "질문 문체 참고 자료"로 쓴다.** 실사용 질문 100개쯤 훑어
그 패턴을 Validation 변형 프롬프트의 few-shot 예시로 넣는다.
나중에 커버리지 공백(사료·행동 문제 등 우리 데이터에 없는 주제) 탐색에도 쓸 수 있다.

## 데이터 추가에 대한 원칙

### 인덱싱 재구축이 필요한가

| 상황 | 필요한 작업 |
|---|---|
| 같은 모델로 한국어 데이터 추가 | **INSERT만** (HNSW는 증분 삽입 지원) |
| IVFFlat 사용 중 + 대량 추가 | INSERT + **REINDEX** (중심점이 데이터를 대표 못 하게 됨) |
| 다국어 대응 위해 모델 교체 | **전체 재임베딩 + 스키마 확인** |

모델 교체 시 차원 확인 필수:
`vector(768)` 컬럼에 1536차원 모델을 넣을 수 없고,
**pgvector HNSW 인덱스는 `vector` 타입 기준 2000차원이 상한**이다.
3072차원 모델을 쓰려면 `halfvec`(4096까지) 또는 차원 축소가 필요하다.

### "중복만 아니면 성능이 좋아진다"는 착각

**검색은 제로섬이다.** `top_k=3`이면 어떤 데이터를 넣든 3개만 뽑힌다.
새 문서는 지식을 추가하는 게 아니라 **기존 좋은 문서와 그 3자리를 놓고 경쟁**한다.

```
기존:   질문 → [좋은 QA, 좋은 QA, 좋은 QA]        → 좋은 답변
추가후: 질문 → [좋은 QA, 깨진 논문조각, 좋은 QA]  → 품질 하락
```

질 낮은 데이터가 특히 위험한 이유:
1. **긴 청크 편향** — 한 청크에 여러 주제가 섞이면 어떤 질문에든 어중간하게 걸린다.
   반면 QA는 주제가 하나로 또렷하다
2. **LLM은 주어진 컨텍스트를 신뢰한다** — 깨진 문장·영어 원문이 그대로 인용된다
3. **모순** — 논문 지침과 QA 실무 조언이 다를 때 판단 근거가 없다

### 언제 데이터 추가가 답인가 — 병목부터 진단

- **답이 될 문서가 아예 없어서 실패** → 데이터 추가가 답.
  치과 879건·안과 1,085건처럼 얇은 영역이 해당 가능성 있음
- **문서는 있는데 검색 순위가 낮아서 실패** → 데이터를 늘리면 **악화된다.**
  리랭커·하이브리드 검색으로 풀 문제

이 둘을 구분하지 않고 데이터부터 늘리면 십중팔구 손해다.

## 작업 순서

1. **평가 기준선** — Validation을 인덱스에서 빼고 Recall@k 측정
2. **리랭커 도입** — 데이터 추가보다 투자 대비 효과가 크다.
   현재 실패의 대부분은 "문서가 없어서"가 아니라 "순위가 낮아서"일 가능성이 높다
3. **실전 문체 검증** — 구어체 변형 질문으로 성능 낙폭 측정, 필요시 query rewriting
4. **데이터 추가** — 위 3개를 마치고 커버리지 공백이 수치로 확인될 때만
