## 현재 상태 (2026-08-13 재설계)

이전 시도(전체 21,606건 임베딩 → pgvector 적재 → 검색 확인)는 **측정 기준 없이

이번에는 **모든 선택을 측정으로 정한다.** 아래 결정은 그 전제로 다시 잡은 것이다.
직전 시도의 실측 기록은 Notion `🧪 RAG 학습 메모 — 임베딩 · 인덱싱 · 리랭커` 참고

## 2026-08-17 추가 — 멘토 피드백 반영

아래 셋이 이 문서에 빠져 있던 것이다. 상세 설계는 [roadmap.md](roadmap.md)에 있고
여기에는 **결정만** 남긴다.

| 결정 | 내용 | 상세 |
|---|---|---|
| **하이브리드 검색** | 벡터 단독 → 벡터 + BM25를 **RRF(k=60)**로 결합. 고유명사·약품명·품종명 질의가 벡터만으로는 약하다. 한국어 BM25는 Postgres 기본 FTS로 불가(`simple`은 공백 분리뿐) → Phase 1은 앱단 `kiwipiepy`+`rank_bm25`, DB 이관은 측정 후 판단 | roadmap §3 |
| **Parent-Child 청킹** | 검색은 작은 조각으로, LLM에는 부모 문단으로. **`content`/`payload` 분리가 이미 그 구조**라 스키마 변경 없이 된다 | roadmap §4 |
| **doc2query** | 확장 데이터(문서·자막)에서 LLM으로 질문을 생성해 그 질문을 `content`에, 원문을 `payload`에 넣는다. 아래 "QA와 청크는 임베딩 성격이 다르다"는 문제를 **인덱스를 계속 질문 모음으로 유지해서** 회피한다 | [data-expansion.md](data-expansion.md) §3 |

⚠️ 셋 다 **같은 후처리가 필수다** — 한 `payload`에 여러 `content`가 붙으므로
검색 결과에서 **`payload` 기준 중복 제거**를 안 하면 top-5가 실질 1건이 된다.
에러가 안 나서 발견이 늦는 종류의 사고다.

**용어:** 아래에서 `Recall@k`로 쓴 것은 정답이 1개인 known-item 설계라
`Hit Rate@k`와 같은 값이다. 실험 기록은 `Hit Rate@k`로 통일한다
([experiments.md](experiments.md)).

## 권장 구성

### 지식베이스는 한 테이블 + `source` 컬럼

```sql
CREATE TABLE documents (
    id          bigserial PRIMARY KEY,

    content     text NOT NULL,        -- ★ 임베딩 대상
    payload     text NOT NULL,        -- ★ LLM에 넘길 본문
    embedding   vector(?),            -- 차원은 모델 확정 후 (아래 참고)

    source      varchar(30) NOT NULL, -- 'aihub_qa' | 'aihub_corpus'

    -- QA 행만 채워짐
    department  varchar(20),          -- 내과/안과/외과/치과/피부과
    life_cycle  varchar(10),          -- 자견/성견/노령견
    disease     varchar(50),

    -- 청크 행만 채워짐
    doc_title   text,
    chunk_index int
);
```

**`content` / `payload` 분리가 핵심.**

| | `content` (검색용) | `payload` (제공용) |
|---|---|---|
| QA 행 | 질문(`input`) | **답변(`output`)** |
| 청크 행 | 청크 본문 | 청크 본문 (같음) |

QA는 질문으로 찾아 답변을 건네주므로 둘이 다르고, 청크는 찾은 것을 그대로 주니 같다.
이렇게 두면 검색 코드가 행 종류를 몰라도 된다 — `content`로 찾아 `payload`를 반환.

**`source` 컬럼**은 물리적 분리가 아니라 **필터로 구분 가능하게** 하는 장치다.
`WHERE source='aihub_qa'`로 원천데이터를 뺀 A/B가 가능하고,
해로우면 `DELETE WHERE source='aihub_corpus'`로 즉시 되돌린다.
이게 없으면 롤백하려고 전체를 재구축해야 한다.

QA와 청크를 **한 테이블에 두는 이유**: 두 테이블로 나누면 검색할 때마다 각각 뽑아
합쳐야 하고 "후보 20건을 QA와 청크에 몇 대 몇으로 배분할지"를 사람이 정해야 한다.
한 테이블이면 유사도 순서대로 섞이고, 그 결과가 좋은지는 지표 2로 재면 된다.

### 임베딩 대상

QA는 **질문(`input`)** 을 인덱싱한다. 사용자 질문 ↔ 저장된 질문 매칭이 의미적으로
더 잘 맞고, input의 82%가 실제 의문문 형태라 이 전략이 유효하다.
(근거가 추정이므로 지표 1로 "질문만 vs 질문+답변"을 재서 확정할 것.)

`instruction`은 인덱싱하지 않는다 (40종 변형이지만 전부 같은 말, 노이즈).

⚠️ **QA와 청크는 임베딩 성격이 다르다.**

```
사용자 질문 ↔ 저장된 질문       (질문 ↔ 질문, 대칭)
사용자 질문 ↔ 논문 본문 조각     (질문 ↔ 서술문, 비대칭)
```

한 인덱스에 섞으면 유사도 점수 스케일이 서로 달라, 어느 한쪽이 **품질이 아니라
형태 때문에** 상위를 독식할 수 있다. cross-encoder는 질문·문서를 같이 보므로 이걸
어느 정도 걸러준다 → **원천데이터를 넣는다면 리랭커는 선택이 아니라 필수.**

### 임베딩 모델 — 기준 두 층

리더보드 순위로 고르지 않는다. 벤치마크는 일반 도메인 평균이고 우리는
**한국어 수의 상담**이라는 좁은 도메인이라 순위가 뒤집힌다.

**1층 — 하드 제약** (측정하기 전에 거르는 것)

| 기준 | 조건 |
|---|---|
| 차원 | ≤ 2000 (pgvector HNSW `vector` 상한. 넘으면 `halfvec`) |
| VRAM | 로컬 GPU에 들어갈 것. **RTX 3050 6GB 확정** — fp16이면 임베딩+리랭커 동시 로드 ~2.2GB로 여유 있음 (아래 "실행 환경") |
| 한국어 | 명시적 지원 ("multilingual"이라도 비중은 천차만별) |
| max_seq_len | 청킹 전략과 정합 |
| 라이선스 | 상업 이용 가능 (메인 프로젝트로 이식 예정) |
| **prefix 요구** | **모델 카드 예제를 그대로 따를 것** |

prefix가 가장 흔한 함정이다. E5 계열은 `query: ` / `passage: `가 필수고, 빠뜨리면
성능이 떨어지되 **에러는 안 나서** "이 모델 별로네"라고 오판하게 된다.

**2층 — 우리 데이터로 측정.** 후보 3개를 같은 조건에서 지표 1로 비교한다.

### 1차 후보 세트 (2026-08-17) — 측정 완료, 폐기

| 역할 | 모델 | 차원 | 골랐던 이유 | Phase 0 실측 |
|---|---|---:|---|---|
| 한국어 튜닝 | `nlpai-lab/KURE-v1` | 1024 | bge-m3 기반 한국어 검색 튜닝 | MRR 0.399 |
| 다국어 범용 | `BAAI/bge-m3` | 1024 | 위와 **같은 base** | MRR 0.395 |
| 경량 | `Alibaba-NLP/gte-multilingual-base` | 768 | 305M, bge-m3의 절반 | MRR 0.335 |

이 세트는 **멘토 피드백 전에 정한 것**이고, 두 개의 질문에 답을 얻었다.

| 질문 | 답 |

| "절반 크기 768차원으로 충분한가?" | ⚠️ **이 질문에는 답하지 못했다** — 아래 |

⚠️ **두 번째 질문은 설계가 잘못돼 있었다.** `gte`는 768차원인 동시에 **305M짜리
다른 모델**이라 "차원"과 "모델"이 같이 바뀐다. gte가 낮게 나온 것(MRR 0.335)을
"768차원이 부족하다"로 읽으면 안 된다 — **원칙 2(한 번에 변수 하나) 위반이다.**

나중에 arctic을 **MRL로 768차원까지 잘라** 다시 재보니 MRR 0.460이 나왔다.
**같은 768차원인데 0.125 차이다.** → **차원이 아니라 모델이 성능을 결정한다.**
상세는 [results/phase0-dimension/](results/phase0-dimension/).

### 2차 후보 세트 (2026-08-18, 확정) — 리더보드 재조사 후

**다시 고른 이유 두 가지:**

1. 1차 세트의 선정 근거였던 "한국어 튜닝이 유리하다"가 **실측으로 깨졌다.**
2. **확장 데이터를 한글/영어 구분 없이 넣기로 정해졌다.** 1차 세트는 이 요구를
   전혀 반영하지 않았다 — "한국어 특화"를 미덕으로 보고 골랐기 때문이다.

#### 선정 기준 9개 — 대부분 우리 실측에서 나온 값이다

| # | 기준 | 값 | 근거 |
|---|---|---|---|
| 1 | **IR 전용 리더보드만 본다** | Retrieval NDCG@5,10 | MTEB 종합점수는 분류·클러스터링·STS가 섞여 검색을 대표하지 않는다 |
| 2 | **차원 ≥ 1024** | 강력 선호 | ⚠️ 근거 정정 — 아래 "기준 2" |
| 3 | **max_seq_len ≥ 2048** | 필수 | R-1(질문+답변) p99가 **1,223토큰** |
| 4 | **파라미터 ≤ 0.6B** | 필수 | 3050 6GB에 리랭커와 동시 상주 + **3종을 끝까지 병행**하려면 비용이 균질해야 |
| 5 | **prefix가 문서화돼 있을 것** | 필수 | 빠뜨려도 에러가 안 나고 성능만 떨어진다 |
| 6 | **Apache-2.0 / MIT** | 필수 | 메인 프로젝트 이식 예정 |
| 7 | **한국어 슬롯: 앵커 대비 ≥ 2점** | 조건부 | ↓ 기준 7 참고 |
| 8 | **세 모델의 차원이 같을 것** | 강력 선호 | 어느 게 이겨도 Phase 2 스키마가 안 바뀐다 |
| 9 | **다국어 — 영어·교차언어 성능이 문서화돼 있을 것** | **필수** | ↓ 기준 9 참고 |

**기준 2 — 원래 근거는 교란돼 있었다.** "gte(768)가 낮으니 768은 안 된다"고 적었으나
gte는 차원과 모델이 같이 달라 분리가 안 된다. **같은 모델을 MRL로 잘라** 다시 재보니:

| 차원 | MRR | 1024 대비 | 판정 |
|---:|---:|---:|---|
| 1024 | 0.463 | — | — |
| 768 | 0.460 | −0.6% | 경계선 (구간 상한이 0에 붙음) |
| 512 | 0.455 | −1.8% | 유의하게 낮음 |
| 256 | 0.445 | −3.8% | 유의하게 낮음 |

→ **768도 실무적으로는 쓸 만하다.** 1024를 택하는 실질 근거는 "768이 나빠서"가
아니라 **손실 없는 최대 차원이고 현 규모(46MB)에서 줄일 이유가 없어서**다.
그래서 이 기준은 "필수"가 아니라 **"강력 선호"**로 내렸다.
데이터가 수십만 건이 되면 **MRL 절단이 카드로 남는다**
([results/phase0-dimension/](results/phase0-dimension/)). ⚠️ MRL 모델에만 유효하다.

**기준 7 — 우리 평가셋의 분해능.** 리더보드에서 KURE-v1(80.76)과 bge-m3(79.30)는
**1.46점** 차인데 우리 데이터에서는 **구분되지 않았다**(95% 구간 폭 ΔMRR ≈ 0.014).
즉 **우리 평가셋의 분해능이 리더보드 1.5점 수준**이다. 그보다 작게 벌어진 모델을
"한국어가 더 낫다"는 이유로 넣으면 슬롯만 쓰고 아무것도 못 가른다.

⚠️ **단, 이 기준은 한국어 성능을 묻는 슬롯에만 적용한다.** 다국어 슬롯의 질문은
"한국어를 얼마나 잃지 않으면서 영어를 얻는가"라 척도가 다르다. 그 슬롯의 조건은
**앵커보다 한국어가 낮지 않을 것 + 기준 9**다.

**기준 9 — 왜 필수인가.** 확장 데이터(유튜브·논문·블로그)를 언어 구분 없이 넣기로
했다. 그러면 필요한 능력이 둘로 갈린다:

| | 필요 능력 | 언제 필요한가 |
|---|---|---|
| 다국어 | 영어 문서는 영어끼리, 한국어는 한국어끼리 잘 검색 | 언어별로 인덱스를 나눌 때 |
| **교차언어** | **한국어 질의로 영어 문서를 찾음** | **한 인덱스에 섞을 때 ← 우리 경우** |

교차언어가 훨씬 어렵고, **한국어 단일 파인튜닝이 가장 먼저 잃는 능력**이다
(한국어 쌍만으로 추가 학습하면 언어 간 정렬이 무너진다).
→ 그래서 "한국어 리더보드 1등"을 그대로 고르면 안 된다.

⚠️⚠️ **이 기준은 지금 측정할 수 없다.** 우리 평가셋은 한국어 전용이다.
현재는 리더보드·모델카드로 **스크리닝만** 가능하고, 실제 검증은 영어/교차언어
평가 슬라이스가 생기는 **Phase 3에서야 된다.** 이걸 명시해두지 않으면 나중에
"다국어라서 골랐는데 한 번도 재본 적이 없다"가 된다.
→ **Phase 3-0(커버리지 공백 진단)에 교차언어 질의셋 제작을 함께 넣을 것.**

#### 측정 결과 (2026-08-18)

**차원 1024 확정. 모델은 3종을 Phase 1까지 병행하고, 최종 1종은 Phase 2 진입 시 정한다.**
주 후보는 `Snowflake/snowflake-arctic-embed-l-v2.0`이다.

| | MRR | 판정 |
|---|---:|---|
| `-ko` 한국어 파인튜닝 | 0.468 | 최고점이지만… |
| **base (다국어)** | **0.463** | **↑와 통계적 동률** (구간 [−0.0116, +0.0023]) |
| `bge-m3` (앵커) | 0.395 | 두 arctic보다 유의하게 낮음 |

**동률이면 잃는 게 없는 쪽을 택한다.** base는 영어·교차언어 능력을 유지하면서
한국어 성능을 (측정 가능한 범위에서) 하나도 내주지 않는다.
`3번 − 2번 = 한국어 특화로 얻는 것`은 **0에 가까웠다** — 즉 확장 데이터를
언어 구분 없이 넣기로 한 결정에 **아무 대가가 없다.**

⚠️ 부수 결과 두 개가 더 중요할 수 있다. 상세는 [experiments.md](experiments.md) Phase 0:
- **한국어 파인튜닝 무효과가 두 계열에서 반복됐다** (KURE-v1/bge-m3, arctic-ko/base)
- **prefix를 빠뜨리면 MRR −16%** — 최고 모델이 최하위로 보인다

**이 구성의 핵심은 2번과 3번의 base가 같다는 것이다.**

```
3번 − 2번  =  한국어 특화로 얻는 것
           =  나중에 영어 데이터를 넣을 때 포기해야 하는 양
```

확장 데이터를 언어 구분 없이 넣기로 한 결정이 만드는 트레이드오프를
**숫자로 재는 구조**다. 차이가 작으면 → 다국어인 2번을 택하는 근거,
크면 → 영어를 별도 컬렉션으로 분리할 근거가 된다.
**어느 쪽이든 근거가 남는다.**

**앵커를 bge-m3로 두는 이유:** Phase 0의 `ranks.csv`가 있어 **질의별로 짝지어**
비교된다. 리랭커 `bge-reranker-v2-m3`와 계열이 같은 것도 Phase 1에서 손이 덜 간다.
`arctic-embed-l-v2.0`이 **`bge-m3-retromae` 기반**이라 셋 다 같은 혈통인 것도
비교를 깨끗하게 만든다.

**KURE-v1을 빼도 손실이 없다.** 질의별 순위가 `ranks.csv`에 남아 있어 언제든 대조된다.

**제외한 모델과 그 이유:**

| 모델 | 한국어 IR | 탈락 사유 |
|---|---:|---|
| `perplexity-ai/pplx-embed-v1-4b` | 82.79 | 기준4 — 4B, 6GB에 리랭커와 같이 못 올린다 |
| `Qwen/Qwen3-Embedding-4B` | 81.37 | 기준4 — 같은 이유 |
| `telepix/PIXIE-Rune-v1.0` | 81.57 | 기준9 — 한국어 특화. **참조점으로만 측정** |
| `nlpai-lab/KURE-v1` | 80.76 | 기준9 + 이미 측정 완료(앵커와 동률) |
| `jinaai/jina-embeddings-v5-text-small` | 80.29 | 기준6 — **CC BY-NC 4.0**, 상업 이용 불가 |
| `microsoft/harrier-oss-v1-0.6b` | 77.49 | 다국어·MIT지만 앵커보다 한국어가 낮다 |
| `google/embeddinggemma-300m` | 78.19 | 기준2 — 768차원 (한국어 IR도 앵커보다 낮다) |
| `intfloat/multilingual-e5-large-instruct` | 77.27 | 기준3 — **max_seq_len 512**, R-1에서 잘린다 |
| `Qwen/Qwen3-Embedding-0.6B` | 75.88 | 앵커보다 한국어가 낮다 |

⚠️ **리더보드는 1층 스크리닝일 뿐이다.** 마지막 갱신일이 표기돼 있지 않고,
무엇보다 **우리 데이터에서 뒤집힐 수 있다** — KURE-v1이 정확히 그랬다.
판정은 항상 2층(우리 평가셋 측정)에서 한다.

#### ⚠️ prefix — `sentence-transformers`가 조용히 속이는 지점

도전자 2종은 **질의에만** `query: `를 붙인다(문서에는 안 붙임).
`03_embed.py`는 리터럴을 손으로 적는 대신 `--query-prompt-name query`로
**모델이 자기 config에 등록한 값**을 쓴다. 추측할 일이 없어진다.
base와 -ko 파인튜닝의 등록값이 `{"query": "query: "}`로 **동일**해서
둘의 비교가 prompt 차이로 오염되지 않는다.

**실측으로 확인한 함정:** `model.prompts`에 이름이 있는지로 검사하면 안 된다.
sentence-transformers 5.x는 모델이 아무것도 등록하지 않아도
`{'query': '', 'document': ''}`를 **기본으로 채워 넣는다** (bge-m3에서 확인).
이름은 항상 존재하고 값만 비어 있으므로, **값이 비면 실패로 봐야** 한다.
안 그러면 "prefix를 넘겼다고 믿지만 실제로는 안 붙은" 상태로 돌아간다.

**비교 단계에서는 DB가 필요 없다.** 19,206 × 1024 float32 = 79MB라 numpy에 통째로
올라가고 브루트포스 유사도가 1초 미만이다. parquet로 임베딩만 뽑아 numpy로 재고,
DB 적재는 **승자 하나만** 한다.
2차 세트는 **셋 다 1024차원**이라 애초에 테이블이 하나로 정해진다.

### 검색 파이프라인

```
사용자 질문(한국어)
  ↓
⓪ prefix 부착     "query: " + 질문        ← ⚠️ 빠뜨리면 MRR −16%, 에러는 안 남
  ↓
① 벡터 검색       pgvector, top 20        ← 널널하게
  ↓
② 리랭킹          cross-encoder, top 5    ← 여기서 정밀도 확보
  ↓
③ 생성            Gemini + 시스템 프롬프트
  ↓
답변 + 출처(진료과/질병)
```

⚠️ **⓪단계를 파이프라인 그림에 넣어둔 이유:** 주 후보(arctic 계열)는 질의에만
`query: `를 붙이는 모델이고, 빠뜨려도 **에러 없이 품질만 떨어진다**
(실측 MRR 0.468 → 0.391). 그림에서 빠지면 구현할 때도 빠진다.
적재 쪽(문서)에는 붙이지 않으며, **prefix는 모델마다 다르다**(`bge-m3`는 없음).

1단계 top_k를 5가 아니라 20으로 잡고 2단계에서 5개를 고르는 구조.
직전 시도 실측에서 **리랭커 상위 5건이 벡터 검색에선 14·15·4·17·10위**였다 —
검색 상위 5건만 썼으면 4건을 놓쳤다는 뜻이고, 후보를 20건까지 넓히는 근거다.
점수 변별력도 검색 0.725~0.675(폭 0.05)에 비해 리랭커는 0.872~0.456(폭 0.42).

**리랭커는 어떤 데이터를 추가하더라도 방파제 역할을 한다** —
질 낮은 데이터가 "정말 관련 있을 때만" 통과하고 평소엔 걸러진다.

⚠️ **리랭커는 오프라인에서 미리 계산할 수 없다.** cross-encoder는 질문과 문서를
같이 넣어야 점수가 나오므로 질문을 모르는 시점엔 원리적으로 불가능하다.
매 요청마다 20건을 그 자리에서 돌린다 → 문서 임베딩과 달리 **로컬 상주 필수.**

### 메타데이터 필터

질문에서 `department` / `life_cycle`을 추출할 수 있으면 검색 범위를 좁힌다.
치과 879건, 안과 1,085건은 필터 없이는 내과 11,049건에 묻힌다.

```sql
WHERE department = '치과'
ORDER BY embedding <=> :q_embedding LIMIT 20
```

`disease`는 77%가 "기타"라 필터로 부적합. 출처 표기용으로만.

### 시스템 프롬프트에 강제할 것

- 검색 결과에 없는 내용은 답하지 말 것 (환각 차단)
- 진단·처방 단정 금지, 동물병원 진료 권유
- **구체적 치료비 언급 금지** — 원본 답변 3%에 비용이 들어있어 그대로 새어나갈 수 있다

## 평가 전략

### 왜 지금 급한가

기준선 없이 데이터를 넣거나 파라미터를 바꾸면 **좋아졌는지 나빠졌는지 알 방법이 없다.**
체감으로는 절대 판단되지 않는다. 직전 시도가 정확히 이 상태로 끝났다.

### ⚠️ 함정 — "Validation을 빼면 자동 채점된다"는 착각

Validation 질문 V에는 짝지어진 정답 답변이 있다. 그런데 **그 QA 쌍은 인덱스에 없다**
(Training만 넣었으니까). V로 검색해 Training QA 5건이 나왔을 때 **무엇이 "맞음"인지
판정할 기준이 없다.** 정답 문서가 인덱스 안에 존재하지 않는다.

`department` + `disease`로 대충 맞추는 방법이 있지만, `disease`의 77%가 "기타"라
내과에서는 무작위로 뽑아도 맞는 수준이 된다. 지나치게 관대한 채점이다.

→ **채점 방법을 두 개로 나눈다. 각각 할 수 있는 일이 다르다.**

### 지표 1 — known-item retrieval (모델·파라미터 비교용)

```
인덱스   전체 21,606건
질의     Validation 질문을 구어체로 변형한 것
정답     그 변형의 원본 행, 정확히 1개
```

정답이 인덱스 안에 딱 하나 있으므로 **채점이 완벽하게 자동화된다.**
Recall@1/5/20, MRR 전부 계산된다. LLM 호출도 사람 판단도 필요 없다.

"전체를 인덱싱하면 자기 자신을 찾아 100%"라는 우려는 여기선 해당 없다 —
**질의가 원본과 다른 문장**이기 때문. 문어체 330자를 구어체 100자로 줄인 것이라
완전일치 매칭이 아니고 실제로 1.0이 안 나온다.

그리고 이건 아래 "실전 문체 검증"과 **같은 작업**이다. 하나 만들어 둘 다 해결한다.

한계를 알고 쓸 것 — 정답이 질의에서 파생된 것이라 **절대 성능은 과대평가된다.**
"Recall@5 = 0.87"을 실력이라 믿으면 안 되고 **모델 A vs B 비교에만** 쓴다.

### 지표 2 — LLM 채점 (절대 성능 + 원천데이터 A/B)

```
질의     Validation 원본 질문 (인덱스에서 제외한 상태)
채점     Gemini에게 "이 검색 결과가 이 질문에 답이 되는가"
규모     2,400건 전부는 비싸니 300건 샘플
```

**원천데이터 청킹 효과는 이 방법으로만 잴 수 있다.** 지표 1은 정답이 "특정 QA 행
1개"라서, 유용한 논문 청크가 1위로 올라와도 **오답으로 채점**된다. 원천데이터가
도움이 되든 말든 점수가 떨어지기만 한다.

| | 지표 1 (known-item) | 지표 2 (LLM 채점) |
|---|---|---|
| 채점 | 완전 자동, 무료 | LLM 호출, 샘플링 필요 |
| 쓰는 곳 | 모델·청킹 파라미터 비교 | 절대 성능, 원천데이터 A/B |
| 절대값 | 과대평가 (상대 비교용) | 신뢰 가능 |

**지표 1을 먼저 만든다.** 싸고 빠르고 반복 가능해서 실험 속도가 완전히 달라진다.

### 실전 문체 검증 (지표 1과 동일 작업)

AI Hub 질문은 평균 330자 문어체로 잘 정제돼 있다. 실사용자는 그렇게 묻지 않는다.

```
AI Hub:  "진돗개의 수컷이 녹내장으로 의심됩니다. 천장 조명이나 휴대폰의
          후레시로 비추어보면 왼쪽 눈에서만 초록빛이 도는 것을..."       (330자)
실사용:  "우리 개 눈이 밤에 초록색으로 빛나는데 정상인가요"              (126자 수준)
```

**우리 시스템은 전자로만 검증됐으므로 후자에서 무너질 가능성이 크다.
데모 때 터지는 전형적인 사고.**

#### 방법: Validation 질문을 구어체로 변형

```
원본(Validation)  →  LLM으로 구어체 축약  →  변형 질문
```

| | Recall@5 |
|---|---|
| 원본 문어체 질문 | 기준선 |
| 구어체로 축약한 같은 질문 | 실전 성능 |

**같은 질문, 문체만 다르다.** 변수가 완벽히 통제되고, 어느 행에서 파생됐는지 알기
때문에 자동 채점된다. "구어체에서 성능이 얼마나 떨어진다"를 숫자로 말할 수 있다.

#### HF 데이터셋(영어)을 그대로 쓰면 안 되는 이유

영어 질문을 그대로 던지면 실패 원인이 **문체 때문인지 언어 때문인지 구분 불가**하다.
실험은 변수 하나만 바꿔야 의미가 있다.
(다국어 임베딩 모델을 쓰더라도 cross-lingual 검색은 동일 언어보다 체계적으로
정확도가 낮아 성능을 실제보다 나쁘게 측정하게 된다.)

번역해서 쓸 수는 있지만 함정이 있다 — LLM이 문장을 **다듬어버린다**:

```
원문:      "my dogs eye is glowing green at night is that normal"
나쁜 번역: "저희 강아지의 눈이 야간에 녹색으로 빛나는 현상이 관찰되는데,
            이것이 정상적인 반응인지 궁금합니다."      ← 다시 문어체, 테스트 의미 상실
좋은 번역: "우리 개 눈이 밤에 초록색으로 빛나는데 정상인가요"
```

오타·짧은 길이·반말 어투·맥락 생략을 **일부러 보존**하라고 명시해야 한다.
게다가 정답 라벨이 없어 자동 채점이 안 된다.

**→ HF 데이터셋은 "질문 문체 참고 자료"로 쓴다.** 실사용 질문 100개쯤 훑어
그 패턴을 Validation 변형 프롬프트의 few-shot 예시로 넣는다.
나중에 커버리지 공백(사료·행동 문제 등 우리 데이터에 없는 주제) 탐색에도 쓸 수 있다.

## 데이터 추가에 대한 원칙

### 인덱싱 재구축이 필요한가

| 상황 | 필요한 작업 |
|---|---|
| 같은 모델로 한국어 데이터 추가 | **INSERT만** (HNSW는 증분 삽입 지원) |
| IVFFlat 사용 중 + 대량 추가 | INSERT + **REINDEX** (중심점이 데이터를 대표 못 하게 됨) |
| 다국어 대응 위해 모델 교체 | **전체 재임베딩 + 스키마 확인** |

모델 교체 시 차원 확인 필수:
`vector(768)` 컬럼에 1536차원 모델을 넣을 수 없고,
**pgvector HNSW 인덱스는 `vector` 타입 기준 2000차원이 상한**이다.
3072차원 모델을 쓰려면 `halfvec`(4096까지) 또는 차원 축소가 필요하다.

### "중복만 아니면 성능이 좋아진다"는 착각

**검색은 제로섬이다.** `top_k=5`면 어떤 데이터를 넣든 5개만 뽑힌다.
새 문서는 지식을 추가하는 게 아니라 **기존 좋은 문서와 그 5자리를 놓고 경쟁**한다.

```
기존:   질문 → [좋은 QA, 좋은 QA, 좋은 QA]        → 좋은 답변
추가후: 질문 → [좋은 QA, 깨진 논문조각, 좋은 QA]  → 품질 하락
```

질 낮은 데이터가 특히 위험한 이유:
1. **긴 청크 편향** — 한 청크에 여러 주제가 섞이면 어떤 질문에든 어중간하게 걸린다.
   반면 QA는 주제가 하나로 또렷하다
2. **LLM은 주어진 컨텍스트를 신뢰한다** — 깨진 문장·영어 원문이 그대로 인용된다
3. **모순** — 논문 지침과 QA 실무 조언이 다를 때 판단 근거가 없다

### 언제 데이터 추가가 답인가 — 병목부터 진단

- **답이 될 문서가 아예 없어서 실패** → 데이터 추가가 답.
  치과 879건·안과 1,085건처럼 얇은 영역이 해당 가능성 있음
- **문서는 있는데 검색 순위가 낮아서 실패** → 데이터를 늘리면 **악화된다.**
  리랭커·하이브리드 검색으로 풀 문제

이 둘을 구분하지 않고 데이터부터 늘리면 십중팔구 손해다.

## 원천데이터 청킹 (이번 범위에 포함)

이전 판정은 "1차 스코프 제외"였으나, **청킹을 직접 익히는 것이 이번 학습 목표**라
포함한다. 다만 조건을 건다.

### 먼저 알아야 할 것

**청킹은 길이 문제를 푸는 기법이지 품질 문제를 푸는 기법이 아니다.**
원천 239건은 영어 원문 잔존 87%, 오역 52%, 표/캡션 혼입 51%다. 잘라도
`"...동공 빛 반사가 없었하였다."` 는 그대로 청크에 들어가고, 오히려 문맥이 더 끊긴다.

### 규모부터 계산할 것

원천 3.9M자를 쪼개면:

| 청크 크기 | 대략 청크 수 | 전체 인덱스 대비 |
|---|---:|---:|
| 400자 | ~10,800 | **36%** |
| 800자 | ~5,400 | 22% |

QA 19,206건에 이만큼이 들어온다 → **검색 후보의 1/4~1/3이 훼손된 논문 조각**이
된다는 뜻. "그냥 추가"가 아니라 상당한 개입이다.

### 순서

1. **전처리를 청킹보다 먼저** — 각주번호(`증가하였다.24`), 표/그림 캡션, 영어 문단 제거.
   여기서 걸러지는 양이 상당할 것
2. **QA만 넣고 기준선 → 원천 추가 후 재측정** (지표 2로). 순서가 반대면 효과를 모른다
3. **청킹 전략 2~3개 비교** — 고정 길이+overlap / 문장 경계 / 문단 경계
4. `source='aihub_corpus'`로 분리해 언제든 `DELETE`로 원복

## 실행 환경 — 로컬 GPU / RunPod

### 로컬 GPU 확정 (2026-08-17) — RTX 3050 6GB

기존에 "4GB인지 8GB인지"로 막혀 있던 항목. **6GB로 확인됐고, 서빙에 충분하다.**

문서에 `임베딩(~2GB) + 리랭커(~2GB) = ~4GB`로 적혀 있던 건 **fp32 기준**이었다.
`use_fp16=True`(삽질 기록에 이미 있음)로 로드하면 절반이 된다.

| 상주 모델 | 파라미터 | fp16 가중치 |
|---|---:|---:|
| 임베딩 — KURE-v1 / bge-m3 (XLM-R-large 계열) | 568M | ~1.1GB |
| 임베딩 — gte-multilingual-base | 305M | ~0.6GB |
| 리랭커 — bge-reranker-v2-m3 | 568M | ~1.1GB |
| 리랭커 — gte-multilingual-reranker-base | 306M | ~0.6GB |

최악 조합(568M + 568M)이라도 가중치 2.2GB + 활성값·CUDA 컨텍스트 ~1.5GB
+ Windows 디스플레이 출력 ~0.7GB ≈ **4.5GB. 6GB 안에 들어간다.** ✅

⚠️ **그런데 진짜 제약은 VRAM이 아니라 지연(latency)일 가능성이 높다.**

리랭커는 매 요청마다 후보 20건을 그 자리에서 돌린다.
568M 모델 × 512토큰 × 20쌍 ≈ 1.2e13 FLOPs이고, 3050의 실효 fp16 성능을
5~6 TFLOPS로 잡으면 **2초 안팎**이 나온다. 채팅 응답으로는 느리다.

이건 계산상의 추정이므로 **Phase 1에서 실측한다.** 만약 맞다면 줄일 수단은 셋:

| 수단 | 효과 | 대가 |
|---|---|---|
| `max_length` 512 → 320 | ~1.6배 | 긴 질문 뒤쪽이 잘림 (input 중앙값 258자라 대부분 무사) |
| 후보 20 → 10 | 2배 | 리랭커가 건질 수 있는 폭이 줄어듦 |
| 리랭커 568M → 306M | ~1.8배 | 정확도 하락분은 측정해야 앎 |

→ **리랭커 크기를 정확도 변수가 아니라 지연 변수로도 봐야 한다.**
[experiments.md](experiments.md) R-2에 두 크기를 따로 기록한다.

### 오프라인 임베딩은 RunPod에서 (연습 목적)

문서 임베딩만 원격 GPU에서 돌리고 결과 파일을 로컬로 가져와 DB에 적재한다.
원격에서 로컬 `localhost:5432`로 직접 연결은 불가능(NAT/방화벽) → **파일 경유.**

```
[RunPod GPU]                              [로컬 3050]
embed.py → embeddings.parquet  ──scp──→  load_db.py  →  pgvector
```

28,000건 × 1024차원 × 4바이트 ≈ 115MB. 왕복에 부담 없다.

**규모를 먼저 알고 시작할 것.** QA 21,606건 임베딩은:

| 환경 | 예상 소요 (모델 1개) | 모델 3개 |
|---|---|---|
| 로컬 3050 6GB | ~20분 | ~1시간 |
| RunPod RTX 3090 / A4000 | ~2분 | ~6분 + 세팅 |

⚠️ **이 작업은 RunPod의 장점이 드러나는 규모가 아니다.** 로컬로도 1시간이면 끝나고,
RunPod 비용은 세팅 포함해도 **$1 미만**이라 가성비를 따질 규모조차 아니다.
그래도 RunPod으로 가는 이유는 **연습**이고, 그건 충분한 이유다 —
Phase 3의 유튜브 STT에서는 원격 GPU가 실제로 필요해진다(아래).

**GPU는 가장 싼 것을 고른다.** 이 규모에서 4090/A100은 낭비다.
RTX 3090이나 A4000(16GB)이면 충분하고 시간당 $0.2~0.3 수준이다.

**Colab이 아니라 RunPod인 실질적 이유:** Colab은 노트북이라 로직이 자꾸 셀로 새어든다.
아래 "노트북에 로직을 쓰지 말 것" 규약이 RunPod에서는 강제된다(SSH로 `.py`를 돌리므로).

### 규약

- **노트북에 로직을 쓰지 말 것.** 로직은 전부 `scripts/embed.py`에 두고
  원격에서는 clone → install → 실행 3줄만
  ```bash
  python scripts/embed.py --model nlpai-lab/KURE-v1 \
      --input data/chunks.jsonl --output out/kure_v1.parquet --batch-size 32
  ```
  모델 3개 비교도 `--model`만 바꿔 세 번 돌리면 된다
- **체크포인트 필수** — RunPod spot은 예고 없이 회수되고 Colab은 유휴 90분에 끊긴다.
  N건마다 parquet 조각으로 flush, 재시작 시 있는 조각은 건너뛸 것
- **출력 규격 고정** — `id | embedding | model_name | dim`.
  `model_name`을 같이 저장해야 질의 모델과 어긋나는 사고를 막는다
- **network volume에 HF 캐시를 둘 것** (`HF_HOME`). bge-m3 가중치가 2.3GB라
  pod을 새로 띄울 때마다 다시 받으면 GPU 시간보다 다운로드가 더 걸린다
- ⚠️ **끄는 걸 잊으면 계속 과금된다.** 작업이 끝나면 pod을 stop이 아니라 terminate.
  volume만 남기면 데이터는 보존된다

### ⚠️ 배치 크기는 로컬 실측값을 그대로 쓰면 안 된다

직전 시도에서 "배치 8이 100보다 빨랐다(패딩 낭비)"는 기록이 있는데,
그건 **VRAM이 빠듯한 로컬에서 길이 정렬 없이** 돌렸을 때 얘기다.

RunPod에서 24GB를 쓰면 전제가 바뀐다 — **길이순으로 정렬해 버킷 배치**하면
패딩 낭비가 사라지고 큰 배치가 유리해진다. 배치 32~64를 다시 재볼 것.
길이 정렬 자체가 임베딩 속도에 가장 크게 듣는 최적화다.

### 어디서 도는가 (헷갈리기 쉬움)

| | 언제 | 어디서 | 비고 |
|---|---|---|---|
| 문서 임베딩 | 오프라인 1회 | **RunPod** | 로컬로도 1시간이면 가능 |
| **질문 임베딩** | 매 요청마다 | **로컬 3050** | 1문장이라 부하 미미 |
| **리랭커** | 매 요청마다 | **로컬 3050** | 20쌍. 지연 병목 후보 |
| 유튜브 STT (Phase 3) | 오프라인 배치 | **RunPod** ★ | 아래 참고 |

**Phase 3의 STT가 원격 GPU를 실제로 필요로 하는 지점이다.**
`faster-whisper large-v3`는 fp16에서 ~4.5GB라 3050 6GB에 단독으로는 올라가지만
(int8_float16이면 ~2.5GB), 영상 100시간을 로컬에서 돌리면 20~30시간이 걸린다.
같은 작업이 원격 24GB 카드에서는 5시간 안쪽이다. **여기서 RunPod이 값을 한다.**

**적재할 때와 질의할 때 반드시 같은 모델·같은 prefix·같은 정규화**여야 한다.
다르면 에러 없이 결과만 이상해져서 발견이 늦는다.
