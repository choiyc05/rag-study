# 실험 기록

**이 프로젝트의 결과물은 동작하는 챗봇이 아니라 이 표다.**
"무엇을 바꿔서 몇 점에서 몇 점이 됐는가"를 남긴다.

작성 규칙은 [roadmap.md](roadmap.md) 참고. **Phase 0 완료 (2026-08-18) — 첫 숫자가 나왔다.**

---

## 기록 규칙

1. **한 행 = 변수 하나 변경.** 두 개를 동시에 바꿨으면 두 행으로 쪼개거나, 쪼갤 수 없으면
   비고에 명시한다. 안 그러면 나중에 어느 쪽이 이겼는지 알 수 없다.
2. **효과가 없거나 나빠진 실험도 지우지 않는다.** 음성 결과가 절반의 가치다.
   "하이브리드를 넣었는데 안 올랐다"도 결과이고, 안 남기면 6개월 뒤에 또 해본다.
3. **직전 행 대비가 아니라 명시한 기준선 대비**로 증감을 적는다.
4. 숫자를 못 재는 변경(리팩터링 등)은 여기 적지 않는다. 커밋 메시지로 충분하다.

## 지표 정의

| 지표 | 정의 |
|---|---|
| `Hit Rate@k` | 정답 문서가 상위 k 안에 있는 질의의 비율. 정답이 1개이므로 `Recall@k`와 같은 값 |
| `MRR` | 정답 순위의 역수 평균. 정답이 얼마나 위에 있는가 |
| `지표 2` | Gemini가 "이 검색 결과가 질문에 답이 되는가"를 채점. 절대 성능용 |

⚠️ **지표 1의 절대값은 과대평가된다.** 질의가 정답 행에서 파생된 것이라
"Hit Rate@5 = 0.87"을 실력이라 믿으면 안 된다. **A vs B 비교에만 쓴다.**

### 짝지은 검정 — 세 개의 판정

같은 질의 2,399건에 대한 역순위 차 + 부트스트랩 2,000회.

| # | 비교 | ΔMRR | 95% 구간 | 판정 |
|---|---|---:|---:|---|
| ① | KURE-v1 → bge-m3 (1차, 같은 base) | −0.0039 | [−0.0108, +0.0028] | **차이 없음** |
| ② | arctic-**ko** → arctic **base** (2차, 같은 base) | −0.0048 | [−0.0116, +0.0023] | **차이 없음** |
| ③ | arctic-ko → bge-m3 | −0.0731 | [−0.0842, −0.0616] | arctic 우세 |
| ④ | arctic-ko → gte(768) | −0.1328 | [−0.1469, −0.1182] | arctic 우세 |

#### ⚠️ 판정 1 — 한국어 파인튜닝은 이득이 없다 (독립 사례 2건)

①과 ②는 **서로 다른 계열에서 같은 결론**이다. 둘 다 base가 같고 변수가
"한국어 파인튜닝" 하나뿐인 대조군인데, **둘 다 차이 없음**이 나왔다.

| | base | 한국어 파인튜닝 | 리더보드 차 | 우리 데이터 |
|---|---|---|---:|---|
| ① | bge-m3 (79.30) | KURE-v1 (80.76) | +1.46 | 차이 없음 |
| ② | arctic-l-v2.0 (80.00) | arctic-l-v2.0-**ko** (82.14) | +2.14 | **차이 없음** |

②는 리더보드에서 **2.14점** 차인데도 안 갈렸다. 기준 7의 임계값("리더보드 2점")이
낙관적이었다는 뜻이기도 하다 — **한국어 파인튜닝 축에서는 2점도 부족하다.**

→ 한 번이면 우연일 수 있지만 **두 계열에서 반복됐다.** 이 데이터·이 평가셋에서
"한국어 특화"는 모델 선택의 근거가 되지 못한다.

#### 판정 2 — 실제 개선은 계열 교체에서 왔다

bge-m3 → arctic 계열이 **ΔMRR +0.073 (상대 +18%)**, Hit@5 0.511 → 0.562.
이게 Phase 0에서 얻은 유일한 실질 개선이다.

#### ⚠️⚠️ 판정 3 — prefix 하나가 모델 순위를 뒤집는다 (E-8)

**같은 모델, prefix만 뺐다:**

| | MRR | Hit@5 |
|---|---:|---:|
| `arctic-ko` + `query: ` (올바른 사용) | **0.468** | 0.572 |
| `BAAI/bge-m3` | 0.395 | 0.511 |
| `arctic-ko` **prefix 없음** | **0.391** | 0.488 |

**−0.077 (상대 −16%).** 그리고 prefix를 빠뜨린 arctic-ko는 **bge-m3보다 낮아 보인다.**

이 프로젝트 문서가 계속 경고해온 *"빠뜨려도 에러가 안 나고 성능만 떨어져서
'이 모델 별로네'라고 오판한다"* 가 정확히 이 숫자다 —
**실제로는 가장 좋은 모델인데 최하위로 기록됐을 것이다.**

⚠️ 오해하지 말 것: "prefix 비대칭이 이득이니 bge-m3에도 붙이면 된다"가 **아니다.**
bge-m3는 prefix 없이 학습됐고 등록된 prompt도 비어 있다. prefix는 **arctic을 올바르게
쓰는 방법의 일부**이며, 모델마다 카드를 따라야 한다는 근거일 뿐이다.

#### 차원 근거 — 처음에 든 근거는 틀렸다

**처음에 "gte(768)가 유의하게 낮으니 768은 안 된다"고 적었다. 교란된 추론이다.**
gte는 768차원인 동시에 **305M짜리 다른 모델**이라, 잰 것은 "768차원이 나쁘다"가
아니라 "이 모델이 나쁘다"였다. **원칙 2(한 번에 변수 하나)를 어긴 것이다.**

제대로 재려면 **같은 모델을 차원만 줄여야** 한다. arctic 계열은 MRL로 학습돼
벡터를 잘라 쓸 수 있고, 이미 뽑은 벡터를 자르면 되므로 재임베딩도 필요 없다.
(`04_evaluate.py --truncate-dim`) 결과 —
원자료 [results/phase0-dimension/](results/phase0-dimension/):

| 차원 | MRR | ΔMRR (1024 대비) | 95% 구간 | 상대 손실 |
|---:|---:|---:|---:|---:|
| **1024** | **0.463** | — | — | — |
| 768 | 0.460 | −0.0030 | [−0.0059, **−0.0000**] | −0.6% (경계선) |
| 512 | 0.455 | −0.0085 | [−0.0127, −0.0042] | −1.8% |
| 256 | 0.445 | −0.0178 | [−0.0226, −0.0130] | −3.8% |

**결론은 유지되지만 이유가 다르다.** 그리고 이 표가 원래 추론이 왜 틀렸는지도
보여준다 — **같은 768차원인데 gte는 0.335, arctic 절단은 0.460이다(차이 0.125).
차원이 아니라 모델이 성능을 결정한다.**

**1024를 쓰는 실질 근거 두 개:**
1. 병행 3종이 **전부 1024**라 모델 선택과 무관하게 스키마가 닫힌다
2. 손실 없는 최대 차원이고, **현 규모(21,606건 = 46MB)에서 줄일 이유가 없다**

⚠️ **통계적 유의 ≠ 실질적 유의.** 768의 손실은 −0.6%로 실무적으로는 무시할 수준이다.
같은 모델을 짝지어 비교했기 때문에 이 정도도 검출된 것뿐이다.
→ **Phase 2에서 DB 용량이나 HNSW 속도가 문제되면 768/512로 줄이는 카드가 있고,
그 대가가 이미 측정돼 있다.** 단 **MRL로 학습된 모델에만 유효하다**(`bge-m3` 제외).

⚠️ **"승자 하나만 남기고 버린다"를 Phase 0에서 하지 않는다.**
Phase 1의 변경(리랭커·하이브리드·의미 분해)이 **모델마다 다르게 들을 수 있기**
때문이다. 지금 하나로 줄이면 그 상호작용을 영영 못 본다.

#### Phase 1 병행 3종과 각자의 역할

| 역할 | 모델 | B-0 MRR | 이 arm이 답하는 질문 |
|---|---|---:|---|
| **주 후보** | `Snowflake/snowflake-arctic-embed-l-v2.0` | **0.463** | 실제 채택 후보. 다국어 유지 |
| **한국어 상한선** | `dragonkue/…-l-v2.0-ko` | 0.468 | **Phase 1을 거쳐도 동률이 유지되는가** |
| **다른 계열 대조** | `BAAI/bge-m3` | 0.395 | **−0.07 격차가 리랭커를 붙인 뒤에도 남는가** |

**세 번째 arm이 가장 실용적인 질문을 담고 있다.** 리랭커가 검색 품질 차이를
흡수해버린다면 임베딩 모델 선택의 중요도 자체가 내려간다 —
그건 Phase 2의 우선순위를 바꾸는 정보다.

`PIXIE-Rune-v1.0`·`KURE-v1`·`gte`는 Phase 0에서 측정만 하고 병행하지 않는다.
`ranks.csv`에 질의별 순위가 남아 있어 필요하면 언제든 대조할 수 있다.

**Phase 1의 기준선(B-0) = 위 표의 세 MRR.** 각 실험은 **자기 모델의 B-0 대비**로
증감을 적는다(모델끼리 섞어서 비교하지 않는다).

선정 기준 9개는 [rag-design.md](rag-design.md) "2차 후보 세트".

⚠️ **기준 9(다국어·교차언어)는 아직 검증되지 않았다.** 우리 평가셋이 한국어 전용이라
스크리닝만 했다. 검증은 roadmap **Phase 3-0b(교차언어 평가 슬라이스)**에서 하며,
**영어 문서를 인덱스에 넣기 전에** 만들어야 기준선이 남는다.

### 절대값이 낮은 것에 대해 (Hit@5 0.56)

로드맵은 "Hit@5가 0.87쯤 나와 과대평가될 것"을 우려했으나 실측은 0.51~0.57이다.
구어체 변형이 **336자 → 34자**로 정보를 덜어냈기 때문이다. 원문의 여러 갈래 중
한 갈래만 남은 짧은 질의로 그 원문을 되찾는 문제라 "자기 자신 찾기"가 아니다.

→ **평가셋이 포화되지 않았다.** 실제로 이 평가셋은 모델 간 차이를 잘 갈랐고
(6종이 0.335~0.468로 벌어짐), prefix 유무 같은 미세한 조건 차이까지 잡아냈다.

### 하위 그룹 — R-6의 근거가 모든 모델에서 반복된다

| 그룹 | 건수 | arctic-ko | **arctic base** | PIXIE | KURE-v1 | bge-m3 | gte |
|---|---:|---:|---:|---:|---:|---:|---:|
| 복합 질문 파생 Hit@5 | 901 | 0.502 | 0.483 | 0.482 | 0.434 | 0.451 | 0.351 |
| 단일 주제 파생 Hit@5 | 1,498 | 0.614 | 0.609 | 0.608 | 0.555 | 0.547 | 0.467 |
| **격차** | | **−11.2%p** | **−12.6%p** | **−12.6%p** | **−12.1%p** | **−9.6%p** | **−11.6%p** |

**모델을 바꿔도 격차가 안 없어진다 — 오히려 좋은 모델에서 더 벌어진다.**
주 후보(arctic base)의 격차 −12.6%p는 bge-m3의 −9.6%p보다 크다.
단일 주제 질의에서 얻은 개선분(+0.062)이 복합 질문에서는 절반만(+0.032) 나타났기
때문이다. **R-6(긴 QA 의미 분해)이 겨냥한 지점은 모델 교체로 풀리지 않고,
모델이 좋아질수록 상대적으로 더 두드러진다.**

⚠️ **R-4(메타데이터 필터)의 전제는 여전히 확인되지 않았다.** 진료과별 Hit@5가
평평하다(1차 세트에서 0.47~0.57). 얇은 진료과가 특별히 나쁘지 않다.
R-4는 기대 효과를 낮게 잡고 접근할 것.

### R-2a 판정 (2026-08-18) — 원자료 [results/phase1-r2a/](results/phase1-r2a/)

**세 arm 모두 올랐다. 기법이 진짜다.** 95% 구간이 셋 다 0을 제외한다
(A [+0.0115, +0.0358] · K [+0.0081, +0.0332] · B [+0.0708, +0.0961]).

#### ⚠️ 지연 걱정은 해소됐다 — 추정이 4배 비관적이었다

로드맵은 "3050에서 20쌍 리랭킹 2초 안팎"으로 보고 **Phase 1의 첫 벽**으로 지목했다.
실측 **e2e p95 573~626ms**다(검색 p50은 0.24ms로 무시 가능). 568M을 그대로 쓴다.

→ **R-2b(306M)·R-2c(`max_length` 320)의 성격이 바뀌었다.** 지연을 줄이려는 실험이
아니라 **"정확도를 얼마나 잃지 않고 더 싸게 갈 수 있나"**를 묻는 실험이 된다.

⚠️ 지연은 **한 요청 = 질의 1건 × 후보 20쌍**으로 쟀다. 정확도 실행은 16질의씩 몰아서
돌리는데 그 배치로 재면 실제보다 좋아 보인다. **LLM 생성은 빠져 있고** 검색은 로컬
numpy 브루트포스다 — Phase 2에서 pgvector와 생성이 붙으면 다시 재야 한다.

#### ⚠️⚠️ 리랭커가 임베딩 모델 격차의 87%를 흡수했다

**이게 3종 병행이 아니면 볼 수 없었던 결과다**(위 이유 ①).

| 비교 | ΔMRR | 95% 구간 | 판정 |
|---|---:|---:|---|
| **B-0**: A → bge-m3 | **−0.0683** | [−0.0801, −0.0562] | A 우세 |
| **R-2a**: A → bge-m3 | **−0.0087** | [−0.0164, −0.0007] | A 우세(경계) |
| B-0: A → K | +0.0048 | [−0.0023, +0.0116] | 차이 없음 |
| R-2a: A → K | +0.0014 | [−0.0032, +0.0062] | 차이 없음 |

Phase 0에서 "계열 교체(+0.073)가 유일한 실질 개선"이었는데, **리랭커를 붙이자 그
개선의 대부분이 무의미해졌다.** bge-m3도 리랭킹 뒤에는 0.478로 arctic(0.487)에 붙는다.
통계적으로는 여전히 유의하지만 **−0.009는 모델 선택의 근거가 되기 어렵다.**

→ **Phase 2의 우선순위가 바뀐다.** "어느 임베딩 모델을 적재할까"에 쓸 시간을 줄이고
리랭커를 전제로 한 구성(후보 수·리랭커 크기·지연)에 쓰는 게 맞다.
→ **질문 ②도 답이 나왔다.** A와 K의 동률이 유지됐고 격차가 오히려 더 줄었다
(+0.0048 → +0.0014). **다국어인 A를 택하는 근거가 한 겹 더 단단해졌다.**

#### Hit@20은 B-0과 정확히 같다 — 정상이며, 리랭커의 상한이기도 하다

리랭킹은 후보 20건 **안에서만** 순서를 바꾸므로 정답이 top-20에 있느냐는 바뀔 수 없다.
세 arm 모두 소수점 셋째 자리까지 같다(A 0.693 · K 0.704 · B 0.664) —
**채점이 의도대로 돌았다는 확인**이다.

→ **리랭커의 천장은 벡터 검색의 Hit@20이다.** A는 0.693이 상한이고, 이걸 올리려면
**후보 자체를 넓히는** 실험(R-3 하이브리드 · R-5 후보 50)이어야 한다.

#### R-6의 몫을 리랭커가 절반 가져갔다

| arm | B-0 격차(복합−단일 Hit@5) | **R-2a 격차** | 회복분 |
|---|---:|---:|---:|
| A | −12.6%p | **−6.9%p** | 5.7%p |
| K | −11.2%p | **−5.7%p** | 5.5%p |
| B | −9.6%p | **−5.9%p** | 3.7%p |

Phase 0의 발견은 "복합 질문 격차는 **모델 교체로 안 풀린다**"였다. 리랭커는 세 모델
전부에서 그 격차를 절반으로 줄인다 — 후보 안에만 들어와 있으면 cross-encoder가
질문과 문서를 같이 보고 골라내기 때문이다.

→ **R-6(의미 분해)은 여전히 필요하지만 기대 효과를 낮춰 잡는다.** 남은 −6%p가 R-6의
몫이고, 그중 **정답이 top-20에 아예 못 든 경우**는 리랭커가 손댈 수 없어 R-3/R-6의 영역이다.

### 3종을 병행하는 이유 — 이 표에서만 보이는 것

**① 모델 간 격차가 살아남는가.** B-0에서 A와 B는 −0.068 벌어져 있다.
리랭커(R-2)를 붙인 뒤에도 그 격차가 남으면 임베딩 모델 선택이 중요한 것이고,
**흡수되면 중요도가 내려간다** — Phase 2에서 무엇에 시간을 쓸지가 바뀐다.

**② A와 K의 동률이 유지되는가.** Phase 0에서 둘은 통계적 동률이었다.
Phase 1의 변경이 한쪽에만 유리하게 작용하면 그때 갈린다.
**갈리지 않으면 다국어인 A를 택하는 근거가 더 단단해진다.**

**③ 개선이 모델 특유인지 일반적인지.** 세 모델에서 모두 오르면 그 기법이 진짜다.
한 모델에서만 오르면 그 모델의 약점을 메운 것일 뿐이다 —
**둘은 전혀 다른 결론인데 단일 모델로는 구분되지 않는다.**

⚠️ **비용:** 실험 9개 × 3종. 재임베딩이 필요한 건 R-1과 R-6뿐이고
(모델당 5분 → 실험당 15분), 나머지는 이미 뽑은 벡터를 재사용한다.
리랭커·BM25 실험은 검색 단계만 다시 도는 것이라 부담이 작다.

### 기록 규칙 (Phase 1 한정)

- **한 행 = 변수 하나.** 3종은 변수가 아니라 **같은 변수를 3번 확인하는 것**이다
- **판정 칸은 "3종 모두" / "A만" 처럼 어느 arm에서 들었는지 적는다.** 이게 위 ③이다
- **음성 결과도 지우지 않는다.** "리랭커를 붙였는데 A에서만 올랐다"도 결과다

**지연 컬럼을 반드시 채운다.** 리랭커는 매 요청마다 20건을 돌리므로 정확도가 올라도
응답이 3초가 되면 서비스로 못 쓴다. **정확도와 지연을 같이 봐야 판단이 된다.**
지연은 모델과 무관한 항목(리랭커 비용)이 대부분이라 arm별로 나눠 적지 않아도 된다.

⚠️ **R-2는 정확도보다 지연 실측이 먼저다.** 로컬 GPU가 RTX 3050 6GB인데
568M 리랭커 × 512토큰 × 20쌍이면 **2초 안팎**으로 계산된다. 사실이면 정확도 비교를
하기 전에 구성부터 바꿔야 한다. 측정 환경(GPU·`max_length`·배치)을 비고에 반드시 적을 것.

⚠️ **R-6은 대상을 나눠서 잰다.** 전체 평균만 보면 효과가 묻힌다.
Phase 0 실측에서 **복합 질문 파생이 단일 주제 대비 9~13%p 낮고 6종 전부 그렇다.**
분해 대상이 된 행에서 나온 질의만 따로 집계할 것 —
전체가 그대로여도 해당 구간이 올랐으면 성공이다.

⚠️ **R-4는 기대 효과를 낮게 잡는다.** "치과 879건이 내과 11,049건에 묻힌다"는
전제가 Phase 0에서 확인되지 않았다 — 진료과별 Hit@5가 평평하다.

⚠️ 필터를 걸면 HNSW 후보가 조용히 반토막 난다(`hnsw.iterative_scan` 확인).
R-4의 결과가 이상하면 이걸 먼저 의심할 것.

## Phase 3 — 데이터 확장 A/B

지표 1로는 잴 수 없다 — 정답이 "특정 QA 행 1개"라서, 유용한 신규 청크가 1위로 올라와도
**오답으로 채점된다.** 확장 데이터의 효과는 **지표 2(LLM 채점)로만** 잴 수 있다.

| ID | 추가한 소스 | 건수 | 인덱스 비중 | 지표 2 | Δ | 판정 |
|---|---|---:|---:|---:|---:|---|
| D-0 | **기준선** (AI Hub QA만) | 21,606 | 100% | | — | — |
| D-1 | + AI Hub 원천 청크 | | | | | |
| D-2 | + 유튜브 **의미 청킹** (전략 C) | | | | | |
| D-3 | + 유튜브 **doc2query만** (전략 B) | | | | | |
| D-4 | + 유튜브 **C + B 병행** | | | | | |

같은 원본 데이터를 세 방식으로 넣어 비교하므로 변수가 통제된다.
**D-2가 기본안이고, D-4가 "돈 써서 더 좋아지는가"를 묻는다.**
D-3은 순수 비교용이며 실제 채택 후보가 아니다 — 커버리지가 깎이므로.

**판정 기준: `D-4 − D-2`가 doc2query의 순수 기여분이다.**
이게 작으면 LLM 호출 비용과 재현성 손실을 감수할 이유가 없다.

**커버리지 공백 질의셋에서도 따로 잴 것.** 전체 평균은 그대로인데 사료·행동 질문만
좋아졌다면 그게 성공이다. 평균만 보면 그 개선이 안 보인다.

| `--fp16`이 `store_true` + `default=True` | 켤 수만 있고 **끌 수가 없는 플래그.** `argparse.BooleanOptionalAction` |
| OOM이 작업 90% 지점에서 터짐 (예방) | 배치를 길이 **내림차순**으로 돌리면 가장 무거운 배치가 맨 처음에 온다 → 시작 직후에 드러난다. 실측 VRAM 3.3GB/6GB로 여유 있었다 |
| **prefix를 빠뜨렸는데 에러가 안 남** | **실측 MRR −0.077(상대 −16%).** 최고 모델이 최하위로 보인다(E-8). `--query-prompt-name`으로 **모델 등록값**을 쓸 것 |
| **`model.prompts`에 이름이 있는데 prefix가 안 붙음** | sentence-transformers 5.x가 등록이 없어도 `{'query': '', 'document': ''}`를 **기본으로 채운다**(bge-m3에서 확인). 이름 존재가 아니라 **값이 비었는지**로 검사해야 한다 |
| 리더보드 상위 모델을 골랐는데 우리 데이터에서 안 갈림 | **한국어 파인튜닝 축에서 리더보드 2.14점 차가 동률로 나왔다**(arctic base vs -ko). 우리 평가셋 분해능은 ΔMRR ≈ 0.014 |
| **예비 실행(`--limit 200`)의 Δ가 +0.214였는데 전체는 +0.024** | R-2는 200건, 기준선은 2,399건이라 **질의 집합이 달랐다.** 부분집합의 평균을 전체 평균과 비교한 것 — 10배 부풀려 보였다. `--limit`이면 Δ를 아예 찍지 않도록 막았다 |
| **arm을 하나 추가했더니 기존 arm의 95% 구간이 바뀜** | 부트스트랩이 **하나의 난수열을 이어 쓰고 있었다.** 앞 비교가 소비한 만큼 뒤가 밀린다. 판정은 안 뒤집혔지만 표를 믿을 수 없게 된다 → **비교마다 시드를 다시 잡는다**(공통난수법이라 오히려 낫다). 2026-08-18 수정, 4번째 소수점이 바뀐 값 4개를 갱신 |
| **결과 폴더 2개가 어떤 명령으로도 재현되지 않음** | `phase0-dimension`·`phase0-prefix-ablation`이 손으로 조립돼 있었다(`"arctic-base @ 1024d"` 같은 라벨을 만드는 코드가 없었다). `--truncate-dim 1024,768,...` 스윕과 `--emb-dir` 반복 인자를 넣어 **명령 한 줄로 재현되게** 고쳤다. 재현 명령은 각 폴더 README |

검색 상위 5건만 썼으면 4건을 놓쳤다는 뜻이고, 후보를 20건까지 넓히는 근거다.
