# 데이터 확장 전략

AI Hub QA 21,606건 위에 데이터를 더 얹을 때의 방법론.
데이터 실측치는 [dataset-analysis.md](dataset-analysis.md), 설계 근거는 [rag-design.md](rag-design.md).

---

## 1. "QA 형식"이 만드는 제약부터 이해할 것

현재 인덱스는 **질문을 임베딩한다**. `content`(검색 대상)에 들어가는 건 보호자의
질문(`input`)이고, `payload`(LLM에 넘길 것)는 수의사의 답변(`output`)이다.

```
사용자 질문  ─┐
              ├─ 질문 ↔ 질문        대칭(symmetric)
저장된 질문  ─┘
```

그런데 앞으로 모을 데이터는 **거의 전부 문서**다. 블로그 글, 유튜브 자막, 논문, 가이드.
이걸 그냥 청킹해서 같은 테이블에 넣으면:

```
사용자 질문  ─┐
              ├─ 질문 ↔ 서술문      비대칭(asymmetric)
문서 청크    ─┘
```

**한 인덱스 안에 대칭 매칭과 비대칭 매칭이 섞인다.** 유사도 점수의 스케일이 서로 달라서
어느 한쪽이 품질이 아니라 **형태 때문에** 상위를 독식한다. 이 문제는 이미
[rag-design.md](rag-design.md)의 "원천데이터 청킹" 절에서 지적한 것과 같은 것이고,
확장 데이터에는 239건이 아니라 수만 건 규모로 적용된다.

⚠️ **그러니 "데이터를 어디서 모을까"보다 "모은 걸 어떤 형태로 인덱스에 넣을까"가 먼저다.**

## 2. 그 전에 — 양이 부족한가, 주제가 부족한가

[rag-design.md](rag-design.md)에 이미 적어둔 원칙:

- 답이 될 문서가 **아예 없어서** 실패 → 데이터 추가가 답
- 문서는 있는데 **순위가 낮아서** 실패 → 데이터를 늘리면 **악화된다**

AI Hub 21,606건이 커버하는 것은 **5개 진료과의 질병 상담**이다. 그런데 이 서비스의
이름은 "강아지 AI **생활** 비서"다. 다음은 인덱스에 **한 건도 없다:**

| 주제 | AI Hub 커버 | 실사용자가 물어볼 빈도 |
|---|---|---|
| 사료 · 영양 · 간식 | ✗ | 높음 |
| 훈련 · 문제행동 (짖음, 분리불안, 배변) | ✗ | 높음 |
| 산책 · 운동량 | ✗ | 중간 |
| 미용 · 목욕 · 발톱 | ✗ | 중간 |
| 예방접종 · 구충 스케줄 | 일부 | 높음 |
| 비용 · 펫보험 | ✗ (오히려 금지 대상) | 높음 |
| 여행 · 호텔 · 이동 | ✗ | 낮음 |
| 질병 진단 · 치료 | **✓ 21,606건** | 높음 |

→ **확장의 축은 "양"이 아니라 "주제"다.** 내과 QA를 5,000건 더 넣어도
검색 상위 5자리를 놓고 기존 좋은 QA와 경쟁만 할 뿐이다(제로섬).
반면 사료·행동은 지금 **아무리 검색해도 답이 없다.**

**Phase 3-0에서 할 일:** 커버리지 공백 진단 스크립트.
HF `Sr523/big-red-bark-chat-evaluation`(실사용 로그 12,385건)의 질문을 번역/샘플링해
현재 인덱스로 검색 → 리랭커 점수가 임계값 아래인 질문을 모은다.
**"우리가 답 못 하는 질문 목록"이 곧 수집 대상 목록이다.** 감으로 정하지 않는다.

## 3. 세 가지 편입 전략

모은 데이터를 인덱스에 넣는 방법은 셋뿐이다.

| | A. 네이티브 QA | B. doc2query | C. 원문 청크 직접 |
|---|---|---|---|
| 원본 형태 | Q&A 게시판 | 문서 / 자막 | 문서 / 자막 |
| `content` (검색) | 원본 질문 | **LLM이 생성한 질문** | 청크 본문 |
| `payload` (제공) | 원본 답변 | 원문 청크 | 청크 본문 |
| 인덱스 정합성 | 완벽 (기존과 동일) | 좋음 (대칭 유지) | 나쁨 (비대칭 혼입) |
| 추가 비용 | 없음 | 청크당 LLM 1회 | 없음 |
| 리스크 | 소스 품질 편차 | 생성 질문이 빗나감 | 점수 스케일 오염 |

### A. 네이티브 QA 수집

이미 질문↔답변 쌍인 소스를 찾는다. 스키마에 그대로 들어가므로 **가장 싸고 안전하다.**
품질 필터링만 하면 된다(답변 길이 하한, 수의사 답변 여부, 채택 여부).

### B. doc2query — 문서를 질문으로 감싸기 ★ 권장

문서 청크 하나에서 **"이 청크가 답이 될 수 있는 질문" 3~5개를 LLM으로 생성**하고,
생성된 질문을 `content`에, 원문 청크를 `payload`에 넣는다.

```
원문 청크: "강아지 분리불안의 초기 징후는 보호자가 외출 준비를 시작할 때부터
            나타난다. 신발을 신거나 가방을 드는 행동에 반응해 ..."
                          ↓ LLM 생성
행1  content="강아지가 나갈 때만 되면 낑낑거려요"        payload=위 청크
행2  content="분리불안 초기 증상이 뭔가요"                payload=위 청크
행3  content="외출 준비하면 강아지가 이상해져요"          payload=위 청크
```

**왜 이게 맞는가:**
1. 인덱스가 계속 "질문 모음"으로 유지된다 → 대칭성 보존, 점수 스케일 오염 없음
2. `content`/`payload` 분리 구조를 이미 만들어놨으므로 **스키마를 바꿀 필요가 없다**
3. 생성 질문을 **구어체로 뽑으라고 지시**하면, 지표 1에서 측정하려던 "실사용 문체 갭"을
   데이터 쪽에서 미리 메운다 (검색 성능이 아니라 인덱스가 문제를 흡수)
4. 한 청크에 여러 질문이 붙으므로 **긴 청크 편향**이 완화된다 —
   긴 청크가 어중간하게 여러 질문에 걸리는 대신, 명시적 질문 여러 개로 쪼개진다

**비용 계산:** 청크 10,000개 × 1회 호출. `gemini-3.1-flash-lite` 기준 감당 가능.
배치로 묶어 한 번에 여러 청크를 처리하면 더 줄어든다.

**함정:**
- 생성 질문이 원문에 없는 내용을 묻는 경우가 있다 → 생성 후 **역검증**
  (생성 질문으로 원문 청크가 top-1에 오는지 확인, 안 오면 폐기)
- 한 청크에서 뽑은 질문끼리 거의 같은 문장이 나온다 → 중복 제거 필요
- `payload`가 중복 저장되므로 저장 공간이 3~5배. 텍스트라 무시 가능하지만
  **같은 청크가 top-5를 독식**할 수 있다 → **검색 후 `payload` 기준 중복 제거 필수**

### C. 원문 청크 직접 투입

AI Hub 원천데이터 239건에 대해 이미 계획된 방식. **리랭커가 붙은 뒤에만 시도한다.**
cross-encoder가 질문과 문서를 함께 보므로 형태 차이를 어느 정도 흡수한다.
B와 C를 **같은 데이터로 A/B 비교**하는 것이 이번 학습의 좋은 실험 소재다.

## 4. 소스 후보

| 소스 | 커버 주제 | 형태 | 편입 | 난도 | 비고 |
|---|---|---|---|---|---|
| 유튜브 (수의사·훈련사 채널) | 행동, 사료, 생활 전반 | 자막/STT | B | 중 | **구어체라 문체 갭이 작다** |
| 동물병원 · 수의사 블로그 | 질병 보조, 생활 | HTML | B | 하 | 품질 편차 큼, 광고글 필터 필요 |
| 반려동물 커뮤니티 Q&A | 실사용 질문 문체 | Q&A | A | 중 | 답변 신뢰도 낮음 → **질문만 평가셋으로** |
| 농림축산검역본부 · 대한수의사회 | 예방접종, 법정 전염병 | PDF/HTML | C 또는 B | 하 | 공신력 높음, 분량 적음 |
| 사료 성분 · 영양 가이드 | 사료 | 표/PDF | B | 중 | 표 구조라 Docling 필요 |
| 수의학 교재 · 논문 | 희귀 질환 백업 | PDF | C | 상 | AI Hub 원천과 같은 훼손 리스크 |

**유튜브를 1순위로 본다.** 이유:
- AI Hub에 없는 **행동·사료·생활** 영역이 유튜브 콘텐츠의 중심이다
- 말로 설명한 것이라 **문어체가 아니다** — 실사용자 질문과 문체 거리가 가깝다
- 자막 API로 텍스트 확보가 상대적으로 쉽다

## 5. 수집 파이프라인 규약

멘토 피드백의 "일회성 수집 탈피". 스크립트는 **여러 번 돌려도 안전해야** 한다.

```
data/
├── raw/                    # 원본 그대로. 절대 수정하지 않음
│   ├── youtube/{video_id}.json
│   └── blog/{source}/{hash}.html
├── normalized/             # 정규화된 중간 산출물 (JSONL)
└── chunks/                 # 청킹 + doc2query 결과
```

| 규약 | 이유 |
|---|---|
| **원본 보존** — `raw/`는 파싱 전 상태로 저장 | 파싱 로직을 고칠 때마다 재수집하지 않는다. 크롤링이 가장 비싸고 가장 잘 깨진다 |
| **멱등성** — 이미 있는 ID는 건너뛴다 | 중간에 끊겨도 이어서 돌린다. Colab/네트워크는 항상 끊긴다 |
| **수집과 파싱 분리** — 다른 스크립트 | 파싱 버그 때문에 수집분을 잃지 않는다 |
| **증분 수집** — 마지막 수집 시각 기록 | "주기적으로 가져온다"의 전제. 전체 재수집은 금물 |
| **소스 메타 필수** — URL, 수집일, 채널/작성자 | 라이선스 분리(§7)와 출처 표기에 둘 다 필요 |

**크롤링 예의** (법적 문제 이전에 차단당하지 않기 위해):
`robots.txt` 확인, 요청 간 지연, 명시적 User-Agent, 응답 캐시.
차단당하면 재수집이 불가능해지므로 이건 매너가 아니라 **가용성 문제**다.

## 6. 유튜브 파이프라인

```
채널/재생목록 목록
  ↓  yt-dlp — 자막 우선 시도
자막 있음 ──────────────────┐
  ↓ 없음                    │
오디오 다운로드              │
  ↓ faster-whisper (STT)    │
전사 텍스트 ────────────────┤
                            ↓
              ⚠️ 문장 복원 (구두점·문단)
                            ↓
                    청킹 → doc2query → 인덱스
```

⚠️ **자동생성 자막을 그대로 청킹하면 안 된다.**

```
원본 자막:  "그래서 이제 강아지가 분리불안이 있으면 이제 보호자가 나갈 때
             막 이렇게 짖고 그러는데 이게 사실은 어 그 전부터 시작이 되거든요"
```

- **구두점이 없다** → 문장 경계 청킹이 불가능하고, 고정 길이로 자르면 말이 끊긴다
- **군더더기가 많다** ("이제", "어", "막") → 임베딩에 노이즈
- **고유명사 오인식** — 약품명·질병명이 엉뚱하게 전사된다. 의료 도메인에선 치명적
- **화자 구분 없음** — 대담 형식이면 누가 한 말인지 사라진다

→ LLM으로 **구두점 복원 + 군더더기 제거** 단계를 반드시 넣는다.
이때 내용을 요약하거나 문어체로 다듬지 말라고 명시할 것 — 구어체가 이 소스의 장점이다.

**품질 게이트:** 수의사/훈련사 등 자격이 확인되는 채널만. 조회수 기준으로 고르면
자극적인 콘텐츠가 올라온다.

## 7. 문서 → Markdown (Docling)

PDF에서 텍스트만 뽑으면 표가 뭉개지고 각주가 본문에 붙는다.
AI Hub 원천데이터 239건이 정확히 그 상태다(각주번호 혼입 51%).

Docling 등으로 **레이아웃을 인식해 Markdown으로** 변환하면:
- `#` 헤딩이 남아 **문단·섹션 경계 청킹**이 가능해진다
- 표가 Markdown 표로 보존된다 (사료 성분표 등에 중요)
- 각주·캡션이 본문과 분리된다

⚠️ **단, 이미 훼손된 텍스트는 Docling으로 복구되지 않는다.**
AI Hub 원천데이터는 이미 텍스트로 추출된 뒤 기계번역까지 거친 상태라
Docling의 대상이 아니다. **새로 수집하는 PDF에만 적용된다.**

## 8. 라이선스 — POC와 배포를 분리해서 생각한다

POC 단계에서는 수집을 멈추지 않는다. 다만 **나중에 걷어낼 수 있게** 만들어둔다.

`source` 컬럼이 이미 그 장치다. 확장하면:

```
source = 'aihub_qa' | 'aihub_corpus' | 'youtube' | 'blog_{도메인}' | 'gov_{기관}'
```

`DELETE FROM documents WHERE source LIKE 'blog_%'` 한 줄로 특정 출처를 뺄 수 있고,
`WHERE source IN (...)`로 A/B도 된다. **출처를 행마다 남기는 것 자체가 리스크 관리다.**

공개 데모/저장소 배포 시점에만 판단하면 되고, 그때 판단할 수 있으려면
지금 출처를 기록해야 한다. `data/`는 이미 `.gitignore`에 있다.

## 9. 상충하는 정보의 처리

멘토 피드백: 상충한다고 지우지 말고 균형 있게 답하도록.

동의하되, **그러려면 시스템 프롬프트와 검색 양쪽에 장치가 필요하다.**

- 검색 단계 — 상위 5건이 한 출처에서만 나오면 반대 의견이 아예 안 보인다.
  `payload` 중복 제거(§3-B)에 더해 **출처 다양성**을 볼지 검토
- 생성 단계 — "참고 문서 간 내용이 다르면 양쪽을 모두 제시하고 어느 쪽이 맞다고
  단정하지 말 것"을 프롬프트에 명시
- 출처 표기 — 답변에 `[출처: AI Hub 수의사 상담]`, `[출처: 유튜브 OOO]`처럼
  **급이 다르다는 걸 사용자가 알 수 있게** 한다

⚠️ 의료 도메인이라 무제한 균형은 위험하다. **공신력 있는 기관 자료와 개인 블로그가
상충하면 균형이 아니라 오도다.** 출처별 신뢰도 등급(`source_tier`)을 두고
리랭킹 점수에 반영할지는 Phase 3에서 측정으로 정한다.
