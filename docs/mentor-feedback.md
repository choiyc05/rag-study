# 멘토 피드백 (2026-08-17)

다른 레포에서 RAG 프로토타입을 빠르게 만들어 시연하고 받은 피드백. **원문 기록용 문서**다.

이 피드백을 기존 설계와 대조해 세운 실행 계획은 [roadmap.md](roadmap.md),
데이터 확장 전략은 [data-expansion.md](data-expansion.md)에 있다.
여기서는 **멘토가 말한 것 자체**를 남긴다 — 나중에 "이건 내 판단인가 멘토 조언인가"를
구분할 수 있어야 하기 때문이다.

> ⚠️ 프로토타입 코드는 이 레포로 가져오지 않는다. 빠르게 만드느라 이해하지 못한 채
> 넘어간 부분이 많아 없는 것으로 치고 계획부터 다시 세웠다.

---

## Part 1 — 데이터 수집 및 초기 분석 전략

### 1-1. 라이선스 및 수집 마인드셋

- **라이선스 걱정 금지.** 현재 POC(개념 증명) 단계이므로 라이선스 제약 때문에 수집을
  멈추지 말 것. 현업에서도 가능한 범위 내에서 최대한 데이터를 확보하는 것이 우선이다.
- **유튜브 데이터 활용.** 자막을 추출하거나, 자막이 없다면 음성을 다운로드해
  **STT(Speech-to-Text)** 로 변환하여 텍스트 내용을 확보할 것.

### 1-2. 크롤링 고도화

- **일회성 수집 탈피.** 단순히 AI에게 "데이터 가져와줘"라고 시키지 말고, 원천 정보가
  많은 사이트를 리서치하여 주기적으로 데이터를 가져올 수 있는
  **크롤링 스크립트를 직접 개발**해야 한다.
- **웹 서치 도구.** 실시간 검색이 필요하다면 `Tavily API`(유료)나 `SearXNG`(로컬 무료)를
  에이전트에 연결할 수 있지만, 성능과 속도 면에서는 **RAG 방식이 더 유리**하다.

### 1-3. 사전 데이터 분석(EDA)

- 데이터를 무작정 넣기 전에 **EDA 스크립트**를 LLM에게 짜달라고 해서 데이터 통계
  (텍스트 길이, 분포 등)를 먼저 확인하고 청킹 전략을 세울 것.

---

## Part 2 — RAG 시스템 설계 및 구현 가이드

### 2-1. 청킹(Chunking) 및 문서 변환

- **Doc to MD.** `Docling` 등을 사용하여 문서를 **마크다운(Markdown)** 형식으로 변환할 것.
  마크다운은 구조가 명확해 의미 단위로 자르기 좋다.
- **청킹 전략.** 데이터 성격에 따라 `Fixed-size`, `Recursive`, `Semantic chunking` 중
  적합한 방식을 선택해야 한다.

### 2-2. 임베딩 모델 및 검색 기술

- **모델 선정 기준.** 리더보드 점수만이 아닌 **임베딩 차원 수, 모델 크기, 언어별 성능,
  속도**를 종합적으로 고려할 것.
- **검색 고도화.** 단순 벡터 검색보다는 키워드 검색을 혼합한 **하이브리드 검색
  (Hybrid Search)** 과 검색 결과의 순서를 재정렬하는 **리랭킹(Reranking)** 적용을 권장.
- **고급 기법.** 정보 손실을 줄이기 위해 큰 덩어리 내에서 작은 조각을 검색하는
  **Parent-Child Chunking** 기법을 검토해 볼 것.

---

## Part 3 — 품질 평가 및 자동화 프로세스

### 3-1. 검색 품질 지표 (Retrieval Metrics)

- **Hit Rate** — 검색 결과 내에 정답이 포함되어 있는가?
- **MRR (Mean Reciprocal Rank)** — 정답이 얼마나 상단에 위치하는가?

### 3-2. 평가 자동화 방법

- 수집한 데이터 중 일부를 랜덤 샘플링하여 LLM에게 **질문-답변 쌍을 생성**하게 함으로써
  평가용 데이터셋을 확보할 것.
- 스크립트를 통해 평가 과정을 자동화하여 수치화된 결과를 기록해야 한다.

### 3-3. 최종 답변 평가

- 검색 품질 평가가 끝난 후 여유가 된다면, **LLM-as-a-judge** 방식을 도입하여 챗봇의
  최종 응답 퀄리티를 평가할 것.

---

## Part 4 — 핵심 조언 및 팁

### 4-1. AI(Claude)를 다루는 전문가의 자세

- 단순한 명령보다는 **"전문가로서 리서치를 먼저 수행하고 단계별로 가이드를 달라"** 는 식으로
  구체적으로 지시하고, 구현 과정에 깊이 개입하여 통제해야 한다.
- 작업 누락을 방지하기 위해 **플래닝(Planning)** 단계를 거치거나 관련 플러그인
  (예: Superpowers)을 활용해 볼 것.

### 4-2. 프로젝트의 본질

- 단순히 기능을 만드는 것보다 **"성능을 어떻게 측정하고, 어떤 실험을 통해 몇 점에서
  몇 점으로 올렸는가"** 를 기록하는 과정이 취업과 실력 향상에 훨씬 중요하다.
- 데이터가 상충되더라도 무조건 삭제하기보다 다양한 의견을 수집해 LLM이 균형 있게
  답변하도록 설계하는 것이 좋다.

## 이 레포에 적용할 때의 해석 — 원문과 다르게 간 것

멘토 조언을 그대로 따르지 않은 지점. **이유를 남겨둔다.**

### 1. To-Do 1번을 바로 실행할 수 없다

"현재 버전의 Hit Rate/MRR 먼저 측정"은 **돌아가는 RAG가 있다는 전제**인데,
이 레포의 백엔드는 더미를 반환하는 골격이다(`_embed()`가 0벡터 768개 반환).
프로토타입 레포의 코드도 가져오지 않기로 했다.

```
멘토 전제:  [돌아가는 RAG] → 측정 → 고도화 → 재측정
이 레포:    평가셋 구축 → 최소 파이프라인 → 측정(기준선) → 고도화 → 재측정
                          ^^^^^^^^^^^^^^^^^^ 이 단계가 하나 더 있다
```

→ roadmap의 **Phase 0**이 이 추가 단계다.

### 2. Hit Rate와 Recall@k는 여기선 같은 값이다

지표 1은 **정답 문서가 인덱스에 정확히 1개**인 known-item 설계라
`Hit Rate@k`와 `Recall@k`가 같은 값이 된다. 기존 문서가 `Recall@k`로 쓰고 있어
혼란이 생길 수 있으므로 **`Hit Rate@k`로 용어를 통일**했다.

### 3. "LLM으로 QA 쌍 생성"은 기존 계획을 대체하지 않는다

| | 구어체 변형셋 (기존) | LLM 생성 QA (멘토) |
|---|---|---|
| 대상 | AI Hub Validation 2,400건 | **정답 라벨이 없는 신규 수집 데이터** |
| 통제 | **완벽** (같은 질문, 문체만 다름) | 느슨 |
| 쓰는 때 | Phase 0~2 | Phase 3 |

AI Hub는 **이미 QA 형태**라 새로 생성할 필요가 없고, 원본 행에서 파생됐다는 사실 덕에
자동 채점이 완벽하다. 반면 크롤링/유튜브 데이터는 정답이 없으므로 멘토 방식이 필요하다.
→ **둘 다 만든다.** 구어체 변형셋이 먼저.

### 4. Docling을 AI Hub 원천데이터에 쓸 수는 없다

원천데이터 239건은 이미 PDF에서 텍스트가 추출되고 기계번역까지 거친 상태로 배포된
것이라(영어 잔존 87%, 각주 혼입 51%) **Docling을 적용할 원본 PDF가 없다.**
→ 새로 수집하는 PDF에만 적용된다.

### 5. 라이선스 — 수집은 자유롭게, 출처는 반드시 기록

POC 단계에서 수집을 멈추지 않는다는 데 동의한다. 다만 **나중에 걷어낼 수 있게**
`source` 컬럼에 출처를 행마다 남긴다. `DELETE ... WHERE source LIKE 'blog_%'` 한 줄로
특정 출처를 뺄 수 있어야 배포 시점에 판단이 가능하다.

### 6. 상충 정보 — 무제한 균형은 의료 도메인에서 위험하다

"지우지 말고 균형 있게"에 동의하되, **공신력 있는 기관 자료와 개인 블로그가 상충하면
균형이 아니라 오도다.** 출처별 신뢰도 등급을 리랭킹에 반영할지는 측정으로 정한다.
(data-expansion.md §9)
