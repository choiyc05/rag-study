## 2. 용어 정리 — Hit Rate와 Recall@k는 여기선 같은 것

혼동을 막기 위해 먼저 못 박는다.

지표 1(known-item retrieval)은 **정답 문서가 인덱스에 정확히 1개**인 설계다.
정답이 1개일 때:

```
Hit Rate@k = (정답이 상위 k 안에 있는 질의 수) / (전체 질의 수)
Recall@k   = (검색된 정답 수) / (전체 정답 수) = 위와 동일
```

→ **같은 값이다.** 문서에서는 멘토 용어를 따라 `Hit Rate@k`로 통일하고,
`MRR`을 함께 기록한다. `Hit Rate@1/5/20` + `MRR`이 표준 리포팅 세트.

### 평가셋 두 종류는 서로를 대체하지 않는다

| | 구어체 변형셋 (기존 계획) | LLM 생성 QA (멘토 제안) |
|---|---|---|
| 대상 | AI Hub Validation 2,400건 | **정답 라벨이 없는 신규 수집 데이터** |
| 정답 | 파생 원본 행, 정확히 1개 | 생성 근거가 된 청크 |
| 통제 | **완벽** (같은 질문, 문체만 다름) | 느슨 |
| 쓰는 때 | Phase 0~2 | Phase 3 (확장 데이터 평가) |

→ **둘 다 만든다.** 순서는 구어체 변형셋이 먼저다(Phase 0에서 필요).

## 3. 신규 설계 — 하이브리드 검색

벡터 검색만으로는 **고유명사·약품명·품종명**이 약하다. "말라뮤트", "심장사상충
예방약 넥스가드"처럼 정확히 그 단어를 찾아야 하는 질의에서 의미 유사도는 오히려 방해가 된다.

```
질문
 ├─ 벡터 검색  (pgvector)      top 30
 ├─ 키워드 검색 (BM25)          top 30
 │        ↓ RRF 결합
 │      후보 20건
 └─────→ 리랭커 → top 5
```

### 한국어 BM25를 어디서 돌릴 것인가 — 결정 필요

⚠️ **PostgreSQL 기본 전문검색은 한국어를 모른다.** `to_tsvector('simple', ...)`는
공백으로만 자르므로 "강아지가"와 "강아지는"이 다른 토큰이 된다.

| 방법 | 장점 | 단점 |
|---|---|---|
| **앱단** `rank_bm25` + `kiwipiepy` 형태소 분석 | 형태소 분석이 제대로 됨. **DB 불필요 → Phase 1 측정에 즉시 사용** | 인덱스를 메모리에 상주. 21,606건은 문제없으나 수십만 건이면 재검토 |
| **DB단** `pg_bigm` (2-gram) 확장 | SQL 한 번에 하이브리드. 운영 단순 | `pgvector/pgvector:pg18` 이미지에 **미포함 → Dockerfile 필요.** 형태소가 아닌 2-gram이라 정밀도 낮음 |

→ **Phase 1은 앱단으로 측정하고, DB단 이관은 Phase 2에서 측정값을 보고 정한다.**
Phase 1은 어차피 DB 없이 numpy로 도는 단계라 앱단이 자연스럽다.

### RRF로 결합하는 이유

벡터 유사도(0.6~0.9)와 BM25 점수(0~30+)는 **스케일이 완전히 다르다.**
정규화해서 가중합하면 그 가중치를 또 튜닝해야 한다. RRF는 점수를 버리고 **순위만** 쓴다:

```
RRF(d) = Σ  1 / (k + rank_i(d))        k = 60 (관례값)
```

튜닝할 파라미터가 사실상 없어서 **첫 하이브리드 시도로 적합하다.**
가중합은 RRF로 개선폭을 확인한 뒤에 시도한다.

## 4. 신규 설계 — Parent-Child 청킹

**검색은 작은 조각으로, LLM에는 큰 조각으로.**

```
검색 대상(child):  "분리불안 초기 징후는 외출 준비 단계에서 나타난다"    (짧음 → 정밀)
LLM 전달(parent):  그 문장이 속한 문단 전체                              (김 → 맥락)
```

작은 청크는 주제가 또렷해 검색 정밀도가 높지만, 그대로 LLM에 주면 맥락이 잘려
답변이 부실해진다. 둘을 분리하면 양쪽을 다 얻는다.

**이미 만들어둔 `content`/`payload` 분리가 정확히 이 구조다.**

| | `content` (child, 검색) | `payload` (parent, 제공) |
|---|---|---|
| AI Hub QA | 질문 | 답변 |
| doc2query | 생성된 질문 | 원문 청크 |
| **Parent-Child** | **작은 청크** | **부모 문단/섹션** |

→ **스키마 변경 없이 세 방식을 같은 테이블에서 A/B 할 수 있다.** 설계를 잘 잡아둔 덕.

⚠️ **필수 후처리:** 같은 parent를 가진 child가 여러 개 걸리면 같은 내용이 top-5를
채운다. **검색 결과에서 `payload` 기준 중복 제거**를 반드시 넣는다. 안 그러면
top-5가 실질 1건이 되는데 **에러가 안 나서 발견이 늦다.**

`scripts/`의 파일명은 **두 자리 숫자 접두사 = 실행 순서**다. 번호순으로 돌리면 된다.

| 파일 | 단계 |
|---|---|
| `00_1_verify_data.py` | EDA — 데이터 전반 ✅ |
| `00_2_analyze_chunking.py` | EDA — 청킹 판단 ✅ |
| `01_prepare_data.py` | **Phase 0-1** ✅ |
| `02_make_evalset.py` | **Phase 0-2** ✅ |
| `03_embed.py` | **Phase 0-3** ✅ |

| `1b_rerank.py` | **Phase 1-b (R-2)** — 리랭커. 지연 실측 + 정확도 |

### 규칙

**`{phase}{step}_이름.py`** — 접두사가 곧 Phase 번호다.

| 접두사 | 대응 |
|---|---|
| `00_` | Phase 0 이전 (EDA) |
| `01_` ~ `04_` | **Phase 0-1 ~ 0-4** |
| `1a_` ~ `1f_` | Phase 1-a ~ 1-f |
| `20_` | Phase 2 |
| `30_` ~ `35_` | Phase 3-0 ~ 3-5 |

**한 단계에 스크립트가 여러 개면 `_1`, `_2`를 더 붙인다.**
`00_1_verify_data.py` / `00_2_analyze_chunking.py`가 그 예다.

파일명만 보고 로드맵의 어느 단계인지 바로 알 수 있게 하는 것이 목적이다.
새 스크립트를 만들면 이 표를 함께 갱신한다.

모든 스크립트는 **저장소 루트에서** 실행하며 경로는 루트 상대경로로 쓴다.
출력 인코딩은 각 스크립트가 `sys.stdout.reconfigure`로 직접 처리한다
(Windows 기본 cp949로는 한글 출력 중 죽는다). 환경변수를 걸 필요 없다.

```bash
backend/.venv/Scripts/python.exe scripts/00_1_verify_data.py
```

⚠️ **Phase 0에서 하나로 줄이지 않는다.** Phase 1의 변경(리랭커·하이브리드·의미 분해)이
**모델마다 다르게 들 수 있고**, 지금 줄이면 그 상호작용을 영영 못 본다.
세 모델에서 다 오르면 그 기법이 진짜고, 한 모델에서만 오르면 그 모델의 약점을
메운 것일 뿐이다 — **단일 모델로는 둘이 구분되지 않는다.**
**DB에 적재할 최종 1종은 Phase 2 진입 시** Phase 1 결과를 보고 정한다.

**③ ⚠️⚠️ "한국어 튜닝이 이긴다"는 전제가 두 번 깨졌다.**

| 대조군 (base가 같고 변수는 파인튜닝 하나) | 리더보드 차 | 우리 데이터 |
|---|---:|---|
| bge-m3 → KURE-v1 | +1.46 | 차이 없음 |
| arctic-l-v2.0 → arctic-l-v2.0-**ko** | +2.14 | **차이 없음** |

**서로 다른 계열에서 반복됐으므로 우연이 아니다.** "한국어 특화"를 이유로
무언가를 고를 때는 반드시 재볼 것. 덕분에 **다국어 base를 택하는 데 대가가 없었다** —
확장 데이터를 한글/영어 구분 없이 넣기로 한 결정과 정확히 맞아떨어졌다.

**③-b ⚠️⚠️ prefix를 빠뜨리면 MRR −16%.** 같은 모델에서 `query: `만 뺐더니
0.468 → 0.391로 떨어졌고, **앵커(bge-m3 0.395)보다 낮아 보였다.** 최고 모델을
최하위로 기록할 뻔한 것이다. `03_embed.py`는 이제 `--query-prompt-name`으로
**모델이 등록한 값**을 쓴다. 리터럴을 손으로 적지 말 것.

**④ 기준선 절대값이 예상보다 훨씬 낮다 (Hit@5 0.56, 0.87 예상).**
구어체 변형이 336자 → 34자로 정보를 덜어낸 탓이다. **평가셋이 안 포화됐다는
좋은 신호**다 — 실제로 6종을 0.335~0.468로 갈랐고 prefix 유무까지 잡아냈다.
**Phase 1의 B-0 기준선 = 위 표의 세 MRR** (A 0.463 · K 0.468 · B 0.395).
각 실험은 **자기 모델의 B-0 대비**로 증감을 적는다.

**⑤ R-6의 근거가 확인됐다 — 그리고 모델 교체로는 안 풀린다.**
복합 질문 파생이 단일 주제 대비 10%p 넘게 낮고 **6종 전부 그렇다.**
주 후보 A의 격차(−12.6%p)가 오히려 bge-m3(−9.6%p)보다 크다 —
모델 개선분이 복합 질문에서는 절반만 나타났기 때문이다.

**⑥ ⚠️ R-4(메타데이터 필터)의 전제는 확인되지 않았다.** "치과 879건이 내과
11,049건에 묻힌다"고 봤는데, 진료과별 Hit@5가 0.47~0.57로 **평평하다.**
얇은 진료과가 특별히 나쁘지 않다. R-4는 기대 효과를 낮게 잡고 접근할 것.

**⑦ ⚠️ 청킹은 하지 않았다 — 의도적이며, R-1에서 조건이 바뀐다.**
Phase 0의 검색 대상은 `content`(질문)뿐이다. 답변(`payload`)은 임베딩하지 않고
LLM에 넘길 원문으로만 들고 있다. 질문은 p99 628토큰이라 `max_seq_len=1024`에서
**초과가 0.03%** — 잘림 문제가 없어 청킹할 이유가 없었다. 고정길이·재귀 청킹을
QA에 적용하지 않는다는 판정은 [dataset-analysis.md](dataset-analysis.md) "텍스트 길이"
절 그대로이고, 이 데이터에 필요한 건 의미 분해(R-6)다.

**그런데 R-1(질문+답변 임베딩)은 전제가 달라진다.** bge-m3 토크나이저 실측:

| 임베딩 대상 | p50 | p95 | p99 | 512 초과 | **1024 초과** | 2048 초과 |
|---|---:|---:|---:|---:|---:|---:|
| `content` (Phase 0) | 134 | 409 | 628 | 2.27% | **0.03%** | 0% |
| `content`+`payload` (R-1) | 308 | 823 | 1,223 | 18.87% | **2.20%** | 0% |

→ **R-1은 반드시 `--max-seq-len 2048`로 돌릴 것.** 1024 그대로면 문서의 2.2%가
조용히 잘리고, 그 손실이 "질문+답변 전략이 별로다"로 잘못 기록된다.
**변수가 둘 섞이는데 에러가 안 나서 발견이 늦는다.** 2048이면 초과 0%다.

**⑧ ⚠️ 기준 9(다국어·교차언어)는 아직 미검증이다.** 2차 세트를 다국어 기준으로
골랐는데 **우리 평가셋이 한국어 전용이라 그 기준을 잰 적이 없다.**
검증은 **Phase 3-0b(교차언어 평가 슬라이스)**이고, **영어 문서를 인덱스에 넣기 전에**
만들어야 기준선이 남는다.

**⑨ 재현 명령** (임베딩은 이미 끝나 있어 재실행하면 "새로 뽑을 것이 없다"로 끝난다):
```bash

backend/.venv/Scripts/python.exe scripts/04_evaluate.py \
  --arm-id dragonkue=E-6 --arm-id embeddings/snowflake=E-7 --arm-id telepix=E-5 \
```

## Phase 2 — DB 적재 + 서비스 연결

여기서 처음 pgvector를 쓴다. Phase 1에서 차원과 구성이 확정된 뒤.

- 스키마 확정 → `models/document.py` 재작성 (지금은 전부 주석이고 설계와 불일치)
- `scripts/load_db.py` — 임베딩과 적재 분리, N건마다 커밋, advisory lock으로 중복 적재 방지
- HNSW 인덱스 — ⚠️ **opclass 불일치 시 에러 없이 완전탐색으로 떨어진다**
- 서비스 배선 — `chat_service._embed()` / `_generate()` 실제 구현, repository 실제 쿼리
  - ⚠️⚠️ **질문 임베딩에 `query: ` prefix를 반드시 붙일 것.** ↓ 아래 절
- 지표 2 (LLM-as-a-judge) 도입 — 절대 성능 측정
- 시스템 프롬프트 — 환각 차단, 진단 단정 금지, **구체적 치료비 언급 금지**(원본 3%에 존재)

### ⚠️⚠️ `_embed()` 구현 시 필수 — prefix

**Phase 1 병행 3종 중 arctic 계열 둘(A·K)은 질의에 `query: `를 붙이는 모델이다.**
문서에는 안 붙인다. 이 비대칭이 모델 사용법의 일부다.
`bge-m3`(B)는 prefix가 없다 — **모델마다 다르므로 적재/질의 코드가 모델을 알아야 한다.**

```python
# 적재할 때 (scripts/load_db.py) — 문서에는 붙이지 않는다
doc_vec = model.encode(content, normalize_embeddings=True)

# 질의할 때 (chat_service._embed()) — 반드시 붙인다
q_vec = model.encode(question, prompt_name="query", normalize_embeddings=True)
#                              ^^^^^^^^^^^^^^^^^^^ 이게 빠지면 조용히 나빠진다
```

**빠뜨리면 어떻게 되는지 실측했다 (Phase 0 대조군):**

| | MRR | Hit@5 |
|---|---:|---:|
| `query: ` 붙임 | 0.468 | 0.572 |
| **빠뜨림** | **0.391** (−16%) | 0.488 |

**에러는 하나도 안 난다.** 검색 결과가 그럴듯하게 나오는데 품질만 낮다.
증상은 "왜 Phase 1에서 잰 것보다 답이 별로지?"로 나타나고, 원인을 여기서
찾기까지 오래 걸린다. 상세는
[results/phase0-prefix-ablation/](results/phase0-prefix-ablation/).

⚠️ **적재와 질의가 같은 모델·같은 prefix·같은 정규화여야 한다.**
`03_embed.py`가 parquet에 `model_name`/`query_prefix`/`passage_prefix`를 기록하는 것도
이 사고를 막기 위해서다. **DB 테이블에도 같은 정보를 남길 것** — 나중에 모델을
바꿨을 때 어느 벡터가 어느 모델 것인지 구분할 방법이 없으면 통째로 다시 뽑아야 한다.

⚠️ **리터럴 `"query: "`를 코드에 하드코딩하지 말 것.** `prompt_name="query"`로
모델 config의 등록값을 쓴다. 모델을 바꿨을 때 prefix가 달라지면 하드코딩한 쪽은
조용히 틀리고, `prompt_name`은 등록이 없으면 드러난다.
(단 sentence-transformers 5.x는 등록이 없어도 빈 값을 채워 넣으므로,
**값이 비었는지**까지 확인해야 한다 — `03_embed.py`의 `resolve()` 참고.)

### 계류 중인 수정 (이 단계에서 함께 처리)

| 대상 | 내용 |
|---|---|
| `compose.yaml` | **`shm_size: 1gb`** — 없으면 `CREATE INDEX`가 `No space left on device`로 죽는다. 디스크가 아니라 컨테이너 공유메모리라 메시지가 원인을 안 가리킨다 |

**완료 기준:** `POST /chat`이 실제 검색 결과 기반으로 답한다. 프론트 연결은 그다음.

## Phase 3 — 데이터 확장

**Phase 1의 측정 인프라가 갖춰진 뒤에만 시작한다.** 순서가 반대면 데이터가 늘어나도
좋아졌는지 알 수 없다 — 직전 시도가 끝난 방식이 정확히 그것이다.

상세는 [data-expansion.md](data-expansion.md).

| # | 작업 |
|---|---|
| 3-0 | **커버리지 공백 진단** — "우리가 답 못 하는 질문 목록"부터 만든다 |
| 3-0b | **교차언어 평가 슬라이스** — 한국어 질의 → 영어 문서. ⚠️ 아래 참고 |
| 3-1 | 수집 스크립트 (주기 실행·증분·멱등) |
| 3-2 | 유튜브 자막/STT → 문장 복원 |
| 3-3 | 청킹 전략 비교 — 고정 / 재귀 / 문장 / **의미(semantic)** / **Parent-Child** |
| 3-4 | **doc2query** 적용 (§data-expansion 3-B) |
| 3-5 | 소스별 A/B — `source` 컬럼 필터로. 나쁘면 `DELETE`로 즉시 원복 |

⚠️ **3-0b가 없으면 임베딩 모델 선정 기준 하나가 영영 미검증으로 남는다.**
확장 데이터를 한글/영어 구분 없이 넣기로 했으므로 2차 후보 세트는 **다국어·교차언어**를
필수 기준(기준 9)으로 골랐다. 그런데 **현재 평가셋은 한국어 전용이라 그 기준을
측정할 수 없다** — 지금은 리더보드·모델카드 스크리닝뿐이다.
한 인덱스에 두 언어를 섞으면 필요한 건 "다국어"가 아니라 **"교차언어"**(한국어 질의로
영어 문서를 찾는 것)이고, 이건 한국어 단일 파인튜닝이 가장 먼저 잃는 능력이다.
→ 영어 문서를 넣기 **전에** 이 슬라이스를 만들어야 한다. 넣고 나서 만들면
기준선이 없어 비교 대상이 사라진다. 상세는 [rag-design.md](rag-design.md) "기준 9".

⚠️ **검색은 제로섬이다.** `top_k=5`면 뭘 넣든 5개만 뽑힌다. 새 문서는 지식을 더하는 게
아니라 **기존 좋은 문서와 그 5자리를 놓고 경쟁**한다. 그래서 3-0(공백 진단)이 먼저다.
