## 2. 용어 정리 — Hit Rate와 Recall@k는 여기선 같은 것

혼동을 막기 위해 먼저 못 박는다.

지표 1(known-item retrieval)은 **정답 문서가 인덱스에 정확히 1개**인 설계다.
정답이 1개일 때:

```
Hit Rate@k = (정답이 상위 k 안에 있는 질의 수) / (전체 질의 수)
Recall@k   = (검색된 정답 수) / (전체 정답 수) = 위와 동일
```

→ **같은 값이다.** 문서에서는 멘토 용어를 따라 `Hit Rate@k`로 통일하고,
`MRR`을 함께 기록한다. `Hit Rate@1/5/20` + `MRR`이 표준 리포팅 세트.

### 평가셋 두 종류는 서로를 대체하지 않는다

| | 구어체 변형셋 (기존 계획) | LLM 생성 QA (멘토 제안) |
|---|---|---|
| 대상 | AI Hub Validation 2,400건 | **정답 라벨이 없는 신규 수집 데이터** |
| 정답 | 파생 원본 행, 정확히 1개 | 생성 근거가 된 청크 |
| 통제 | **완벽** (같은 질문, 문체만 다름) | 느슨 |
| 쓰는 때 | Phase 0~2 | Phase 3 (확장 데이터 평가) |

→ **둘 다 만든다.** 순서는 구어체 변형셋이 먼저다(Phase 0에서 필요).

## 3. 신규 설계 — 하이브리드 검색

벡터 검색만으로는 **고유명사·약품명·품종명**이 약하다. "말라뮤트", "심장사상충
예방약 넥스가드"처럼 정확히 그 단어를 찾아야 하는 질의에서 의미 유사도는 오히려 방해가 된다.

```
질문
 ├─ 벡터 검색  (pgvector)      top 30
 ├─ 키워드 검색 (BM25)          top 30
 │        ↓ RRF 결합
 │      후보 20건
 └─────→ 리랭커 → top 5
```

### 한국어 BM25를 어디서 돌릴 것인가 — 결정 필요

⚠️ **PostgreSQL 기본 전문검색은 한국어를 모른다.** `to_tsvector('simple', ...)`는
공백으로만 자르므로 "강아지가"와 "강아지는"이 다른 토큰이 된다.

| 방법 | 장점 | 단점 |
|---|---|---|
| **앱단** `rank_bm25` + `kiwipiepy` 형태소 분석 | 형태소 분석이 제대로 됨. **DB 불필요 → Phase 1 측정에 즉시 사용** | 인덱스를 메모리에 상주. 21,606건은 문제없으나 수십만 건이면 재검토 |
| **DB단** `pg_bigm` (2-gram) 확장 | SQL 한 번에 하이브리드. 운영 단순 | `pgvector/pgvector:pg18` 이미지에 **미포함 → Dockerfile 필요.** 형태소가 아닌 2-gram이라 정밀도 낮음 |

→ **Phase 1은 앱단으로 측정하고, DB단 이관은 Phase 2에서 측정값을 보고 정한다.**
Phase 1은 어차피 DB 없이 numpy로 도는 단계라 앱단이 자연스럽다.

### RRF로 결합하는 이유

벡터 유사도(0.6~0.9)와 BM25 점수(0~30+)는 **스케일이 완전히 다르다.**
정규화해서 가중합하면 그 가중치를 또 튜닝해야 한다. RRF는 점수를 버리고 **순위만** 쓴다:

```
RRF(d) = Σ  1 / (k + rank_i(d))        k = 60 (관례값)
```

튜닝할 파라미터가 사실상 없어서 **첫 하이브리드 시도로 적합하다.**
가중합은 RRF로 개선폭을 확인한 뒤에 시도한다.

## 4. 신규 설계 — Parent-Child 청킹

**검색은 작은 조각으로, LLM에는 큰 조각으로.**

```
검색 대상(child):  "분리불안 초기 징후는 외출 준비 단계에서 나타난다"    (짧음 → 정밀)
LLM 전달(parent):  그 문장이 속한 문단 전체                              (김 → 맥락)
```

작은 청크는 주제가 또렷해 검색 정밀도가 높지만, 그대로 LLM에 주면 맥락이 잘려
답변이 부실해진다. 둘을 분리하면 양쪽을 다 얻는다.

**이미 만들어둔 `content`/`payload` 분리가 정확히 이 구조다.**

| | `content` (child, 검색) | `payload` (parent, 제공) |
|---|---|---|
| AI Hub QA | 질문 | 답변 |
| doc2query | 생성된 질문 | 원문 청크 |
| **Parent-Child** | **작은 청크** | **부모 문단/섹션** |

→ **스키마 변경 없이 세 방식을 같은 테이블에서 A/B 할 수 있다.** 설계를 잘 잡아둔 덕.

⚠️ **필수 후처리:** 같은 parent를 가진 child가 여러 개 걸리면 같은 내용이 top-5를
채운다. **검색 결과에서 `payload` 기준 중복 제거**를 반드시 넣는다. 안 그러면
top-5가 실질 1건이 되는데 **에러가 안 나서 발견이 늦다.**

## 스크립트 명명 규칙

`scripts/`의 파일명은 **두 자리 숫자 접두사 = 실행 순서**다. 번호순으로 돌리면 된다.

| 파일 | 단계 |
|---|---|
| `00_1_verify_data.py` | EDA — 데이터 전반 ✅ |
| `00_2_analyze_chunking.py` | EDA — 청킹 판단 ✅ |
| `01_prepare_data.py` | **Phase 0-1** ✅ |
| `02_make_evalset.py` | **Phase 0-2** |
| `03_embed.py` | **Phase 0-3** |
| `04_evaluate.py` | **Phase 0-4** |

### 규칙

**`{phase}{step}_이름.py`** — 접두사가 곧 Phase 번호다.

| 접두사 | 대응 |
|---|---|
| `00_` | Phase 0 이전 (EDA) |
| `01_` ~ `04_` | **Phase 0-1 ~ 0-4** |
| `1a_` ~ `1f_` | Phase 1-a ~ 1-f (스크립트가 생긴다면) |
| `20_` | Phase 2 |
| `30_` ~ `35_` | Phase 3-0 ~ 3-5 |

**한 단계에 스크립트가 여러 개면 `_1`, `_2`를 더 붙인다.**
`00_1_verify_data.py` / `00_2_analyze_chunking.py`가 그 예다.

파일명만 보고 로드맵의 어느 단계인지 바로 알 수 있게 하는 것이 목적이다.
새 스크립트를 만들면 이 표를 함께 갱신한다.

모든 스크립트는 **저장소 루트에서** 실행하며 경로는 루트 상대경로로 쓴다.
출력 인코딩은 각 스크립트가 `sys.stdout.reconfigure`로 직접 처리한다
(Windows 기본 cp949로는 한글 출력 중 죽는다). 환경변수를 걸 필요 없다.

```bash
backend/.venv/Scripts/python.exe scripts/00_1_verify_data.py
```

## Phase 0 — 측정 가능한 최소 파이프라인 ★ 여기부터

멘토 To-Do 1번("현재 버전의 Hit Rate/MRR 먼저 측정")에 해당.
다만 **이 레포에는 '현재 버전'이 없다.** 백엔드는 더미를 반환하는 껍데기다.
그러니 Phase 0의 목표는 개선이 아니라 **첫 숫자를 만드는 것**이다.

| # | 작업 | 산출물 |
|---|---|---|
| 0-1 | ~~zip → JSONL 전처리~~ (`scripts/01_prepare_data.py`) | ✅ `data/normalized/aihub_qa.jsonl` 21,606건 (41.2MB) |
| 0-2 | 구어체 변형 평가셋 (`scripts/02_make_evalset.py`) | 질의 500건 + 정답 ID |
| 0-3 | 모델 3개 임베딩 (`scripts/03_embed.py`, **RunPod**) | parquet 3개 |
| 0-4 | numpy 브루트포스 평가 (`scripts/04_evaluate.py`) | Hit Rate@1/5/20, MRR |

**완료 기준:** experiments.md에 **모델 3개의 Hit Rate·MRR 숫자가 채워지고,
임베딩 모델과 차원이 확정된다.**

**이 단계에서 DB는 필요 없다.** 19,206 × 1024 float32 = 79MB. numpy에 통째로 올라가고
브루트포스 유사도가 1초 미만이다. **스키마를 먼저 정하려 들지 말 것** — 차원이
안 정해졌는데 테이블부터 만들면 세 번 다시 만들게 된다.

**재사용:** 파싱 로직은 `scripts/00_1_verify_data.py`에 이미 검증된 것이 있다.
zip을 풀지 않고 그대로 읽어 21,606건을 파싱하므로 여기서 잘라 쓰면 된다.

**주의:** `utf-8-sig`로 읽을 것. BOM 때문에 첫 키가 `meta`로 안 잡힌다.

### 0-1 완료 (2026-08-18) — 다음 단계가 알아야 할 것

- 출력 `data/normalized/aihub_qa.jsonl` — 1행 1 QA, 필드는 rag-design 스키마 + `split`

  지표 2는 Validation을 인덱스에서 빼고 원본 질문으로 묻는다. 이게 없으면 하나를 못 만든다
- `content_len` / `question_marks`를 미리 재뒀다 → Phase 1-f(R-6) 대상 선별용.
  **복합 질문(질문표현 3개+) 3,527건 = 16.3%**
- ⚠️ **Train↔Valid 질문 누수 1건.** 0-2에서 평가셋을 만들 때 이 질문은 제외할 것 —
  Validation 질의의 정답이 Training에도 있어 채점이 애매해진다
- ⚠️ 발견: `department`에 앞 공백이 붙은 행 1건 → `strip()` 처리
  ([dataset-analysis.md](dataset-analysis.md))

**실행 환경 (2026-08-17 확정):** 로컬 **RTX 3050 6GB**, 오프라인 임베딩은 **RunPod**.
막혀 있던 VRAM 항목은 해소됐다 — fp16이면 임베딩+리랭커 동시 로드가 2.2GB라 여유 있다.
상세는 [rag-design.md](rag-design.md) "실행 환경".

0-3은 로컬 3050으로도 모델 3개에 ~1시간이면 끝나는 규모다. RunPod으로 가는 건
**연습 목적**이고 비용은 $1 미만이다. 원격 GPU가 실제로 필요해지는 건 Phase 3의 STT.

→ Phase 1 R-2에서 **실측이 최우선**.

| 대상 | 내용 |
|---|---|
| `compose.yaml` | **`shm_size: 1gb`** — 없으면 `CREATE INDEX`가 `No space left on device`로 죽는다. 디스크가 아니라 컨테이너 공유메모리라 메시지가 원인을 안 가리킨다 |
| `pyproject.toml` | `transformers<5` 고정 (5.x에서 리랭커가 `prepare_for_model` 없음으로 죽음) |
| `repositories/` | 지금 `SourceItem`(스키마)을 반환 중 → `SearchResult(document, score)` dataclass 반환, service가 스키마로 변환 |

**완료 기준:** `POST /chat`이 실제 검색 결과 기반으로 답한다. 프론트 연결은 그다음.

## Phase 3 — 데이터 확장

**Phase 1의 측정 인프라가 갖춰진 뒤에만 시작한다.** 순서가 반대면 데이터가 늘어나도
좋아졌는지 알 수 없다 — 직전 시도가 끝난 방식이 정확히 그것이다.

상세는 [data-expansion.md](data-expansion.md).

| # | 작업 |
|---|---|
| 3-0 | **커버리지 공백 진단** — "우리가 답 못 하는 질문 목록"부터 만든다 |
| 3-1 | 수집 스크립트 (주기 실행·증분·멱등) |
| 3-2 | 유튜브 자막/STT → 문장 복원 |
| 3-3 | 청킹 전략 비교 — 고정 / 재귀 / 문장 / **의미(semantic)** / **Parent-Child** |
| 3-4 | **doc2query** 적용 (§data-expansion 3-B) |
| 3-5 | 소스별 A/B — `source` 컬럼 필터로. 나쁘면 `DELETE`로 즉시 원복 |

⚠️ **검색은 제로섬이다.** `top_k=5`면 뭘 넣든 5개만 뽑힌다. 새 문서는 지식을 더하는 게
아니라 **기존 좋은 문서와 그 5자리를 놓고 경쟁**한다. 그래서 3-0(공백 진단)이 먼저다.
